# Focused code review

Review the requested operation against its explicit contract. Inspect changed code and affected callers, state owners, registration and failure paths. Use source evidence, not a checklist hit alone, to confirm a trigger, cause and consequence. Consider counterevidence and intentional behavior; clean code needs no finding. Missing a preferred technique alone is not a defect.

A value frozen in code is a candidate defect when it has a live source of truth (manifest, config, environment, database, API or a sibling constant) or varies by machine, deployment, tenant or date. Confirm it by comparing, not by reading one file: for each version string, path, host, id, accepted-values set, spelling or name table, regex that mirrors a table, and list copied from another component, look in every supplied file for its source (package and plugin manifests, serializer attributes such as rename rules, the table or constant it mirrors, the other program or API it describes) and compare value by value. A mismatch, or a copy that will not follow its source when the source changes, is the finding; name the context in which the copy breaks. Real protocol and policy constants stay, and a value that looks wrong may be newer than your knowledge. A layer, wrapper, factory, second state owner or service split is a candidate defect when it adds a failure point or a copy of state and no named capability.

Trace the simplest adequate correction across affected paths. Preserve output semantics, ordering, error contracts, supported consumers, operation identity, retry ownership, deadlines and recovery behavior. An error handler is defective when it loses required behavior or hides incomplete work; an intentional terminal or best-effort handler can be valid. Sequential work and fixed limits can be intentional. Only claim measured performance gains from actual comparable measurements.

For cleanup, check dynamic registrations, external consumers, flag prerequisite edges and emergency paths before calling code unused. Absence in sampled telemetry is not proof of disuse. Remove only behavior the supplied contract permits removing.

Keep severity separate from introduced/pre-existing origin. Reconcile prior findings: suppress unchanged resolved issues; reopen the same identity or explicitly link it when a closure premise changes. Cover unchanged callers affected by a changed contract. Group instances of one cause; do not invent nits or duplicates.

Historical memory offers hypotheses. Check applicability, invalidation and failed approaches before reuse; no retrieval score proves current causality. Missing tools or skipped inputs are coverage gaps, not clean reviews. Before reporting a count, a "none found" or a scanner hit, run the same grep or script on a known positive and check its exit status (`scan.py --self-test` for the scanner); never infer absence from truncated output. Do not write incidents or repair code during review-only work. In an authorized repair, reproduce when feasible, correct the cause and verify affected guarantees. Distinguish proposed checks, executed tests, runtime and deployment.

Return material findings with trigger, causal explanation, location, consequence, smallest adequate action and discriminating verification. Report no material findings when supported. Do not fabricate execution or certainty.

# Debug with shared audit principles

```text
identify symptoms, expected behavior, revision and authorized scope
if memory available: search symptoms and inspect candidate context
reproduce when feasible; record original-environment gaps
trace plausible causes through shared state and failure boundaries
predict a check that distinguishes the strongest cause from alternatives
record failed approaches; check the oracle enforces the actual contract
compare the symptom patch with the simplest adequate mechanism repair
repair in scope; run the prediction, reproducer and affected regressions
seek independent critique when available; disclose its actual status
report evidence and gaps
if incident recording authorized: follow debugging-memory/SKILL.md storage checks
```

For a review-only request, investigate and report proposed repairs without applying code changes, writing workflow state or storing incidents unless separately authorized.

Load [shared principles](../code-principles/SKILL.md) and relevant challenge references. For a recurrent, disputed or nontrivial cause follow [the deeper loop](../debug-loop/SKILL.md). For an obvious cause use a short investigate, fix, verify sequence. A past KNOWN_FIX still requires validation against current contracts and verification.

The bundled MCP server `code-audit-debugger` supplies search, detail, store, outcome, status, list, patterns and read_logs. Use actual host-exposed names. If unavailable, report that memory was not checked and continue with source/log/test evidence. Never invent matches or successful storage. Do not write another host's personal assistant memory.

The procedure is host-neutral. On Claude Code the bundled agents (`assessment-orchestrator` and four domain assessors, `root-cause-investigator`, `fix-critique`) provide parallel domain assessment, causal-tree investigation and critique; see [debugging memory](../debugging-memory/SKILL.md#independent-work). Investigate directly when a host lacks agent registration. Independent critique requires an actual independent execution; self-review cannot substitute for it. If unavailable, mark critique UNAVAILABLE and deliver bounded results with that gap disclosed.

Before any incident or outcome write, follow [debugging memory](../debugging-memory/SKILL.md): check `status` and require its actual working directory and configured memory path to match the authorized project or explicitly selected shared corpus. If the destination cannot be established, keep a task report and disclose the storage gap.

Use [review feedback](../code-principles/references/review-feedback.md) for critique/re-review and [incident learning](../code-principles/references/incident-learning.md) for historical outcomes. Share one justified budget across review and repair; do not reset the iteration limit when switching workflows.

Timeouts can leave completed writes behind. Preserve logical identity, reconcile uncertain effects, retry at one layer, choose limits from relevant observations or explicit reasonable assumptions, and propagate the total deadline. Increasing a timeout alone does not prevent duplicate effects.

# Debug Loop — Iterative Root Cause Debugging

A 7-phase debugging loop: investigate via causal tree analysis, hypothesize root cause, implement targeted fix, verify with evidence, score against criteria, pressure-test via critique agent, and report with transparency markers. Iterates up to 5x on failures.

Read [shared principles](../code-principles/SKILL.md) and relevant challenge details before choosing a repair.

## Scope Check

Before entering the loop, assess whether it's warranted. Choose depth from the actual causal uncertainty, recurrence and scope. Retrieval similarity is not calibrated confidence in a fix.

- **Skip the deep loop** for `KNOWN_FIX` only after validating causal fit and current contracts; adapt and verify
- **Skip the loop** for trivial issues: typos, missing imports, obvious config errors where the cause is immediately clear
- **Enter the loop** for a nontrivial or disputed cause, a previous repair that did not hold, an unexplained cross-component failure, or an explicit deep-investigation request. A weak or absent memory match is one input, not an automatic trigger.

## Efficiency

- Terminal output: current phase, key findings (one line each), status changes, failures. No verbose reasoning
- Agent context: minimum needed per job. Pass symptom + relevant findings, not full conversation history
- Load convergence rules reference on demand only when entering iteration

For a repair or restart crossing component boundaries, read [change and failure isolation](references/change-isolation.md). Verify the shared cause and affected callers; a past incident or a small diff does not establish that the current boundary is adequate.

## Phase 1: INVESTIGATE — Gather Evidence and Trace Root Cause

**Goal**: Understand what's actually failing and why, not just what it looks like.

1. **Search memory when available** — use the bundled debugger search tool; inspect candidate context. If unavailable, disclose the gap and continue source investigation.
2. **Reproduce the issue when feasible** — identify exact steps, commands, or conditions that trigger the bug. If the original environment is unavailable, record the causal evidence and limits; distinguish a controlled regression case from reproduction of the original incident.
3. **Trace plausible causes** — inspect callers, state and failure boundaries, rank by evidence and prune with counterevidence. Use an independent investigator only when authorized and available (on Claude Code, the bundled `root-cause-investigator` agent; for an unclear multi-domain symptom, `assessment-orchestrator` and its domain assessors); agent registration is not required for investigation.
4. **Research gate** — if the investigator flags unfamiliar error codes, library behavior, or version-specific issues:
   - Search official sources using a minimal non-sensitive query; never send private code, credentials or logs without authorization
   - Document what was searched and what was found
   - If search is unavailable, document what SHOULD be searched
5. **Assess completeness** — does the investigation explain ALL reported symptoms? Check for multi-causal bugs (2+ independent root causes)

**Output**: Causal tree (with confirmed and pruned branches), reproduction steps, evidence gathered, research performed

## Phase 2: HYPOTHESIZE — State the Root Cause

**Goal**: Commit to a specific, testable hypothesis before writing any fix.

1. **State the root cause hypothesis** with evidence level:
   - **Strong**: Multiple evidence types (code, logs, reproduction) all point to this cause
   - **Moderate**: Some direct evidence plus reasonable inference
   - **Weak**: Mostly inference, limited direct evidence — consider investigating other branches first
2. **Predict verification test**: If this hypothesis is correct, what specific test would prove it?
3. **Predict related symptoms**: What else should be affected if this root cause is real?
4. **If multiple hypotheses exist**, rank by evidence strength. Pursue the strongest first

**Output**: Hypothesis statement, evidence level, prediction test, related symptom predictions

## Phase 3: FIX — Implement Targeted Change

Apply code changes only when the task authorizes repair. For review-only requests, report the supported cause, proposed correction and verification plan; do not apply fixes or write incident/workflow state.

**Goal**: Make the simplest adequate change that addresses the causal mechanism across affected supported paths.

1. **Compare a symptom patch with a causal repair** — trace the existing state owner and affected callers before adding a case-specific exception. A null guard can be correct at a boundary that permits missing data; establish the contract rather than treating every guard as a symptom patch.
2. **Keep changes proportional** — repair the shared mechanism where needed, preserving supported callers and valid counterexamples. Avoid unrelated cleanup or speculative frameworks; minimum adequate means causal coverage, not the fewest changed lines.
3. **Note exactly what was changed and why** — this becomes the evidence trail

**Output**: List of changes with rationale

## Phase 4: VERIFY — Test the Fix with Evidence

**Goal**: Collect concrete evidence that the fix works.

1. **Run the prediction test** from Phase 2 — does it confirm the hypothesis?
2. **Run the original reproduction steps** — is the symptom gone?
3. **Run related test suite** — do existing tests still pass?
4. **Check for regressions** — run broader test suite if available
5. **Verify related symptom predictions** — are the predicted effects present?

Each applicable verification step needs evidence: command output, test results, or observable behavior. Mark a genuinely inapplicable check N/A with its scope reason, or a missing required environment/check UNAVAILABLE with the gap. Neither is PASS. "It should work" is not evidence.

**Output**: Evidence for each verification step

## Phase 5: SCORE — Evaluate Against Criteria

**Goal**: Evidence-based status for each criterion.

Score against these criteria:

| # | Criterion | Method | Pass Condition | Evidence Required |
|---|-----------|--------|----------------|-------------------|
| 1 | Symptom resolved | Reproduction steps | Symptom no longer occurs | Command output or test result |
| 2 | Tests pass | Test suite | All relevant tests pass | Test runner output |
| 3 | No regressions | Broader test suite | No new failures introduced | Test runner output |
| 4 | Root cause addressed | Code review | Fix targets root cause, not symptom | Diff + reasoning |
| 5 | Hypothesis confirmed | Prediction test | Prediction test passes | Test output |

**Every criterion needs an evidence status.** Use PASS with observed evidence, FAIL for an observed unmet criterion, N/A only when genuinely inapplicable to the approved scope, and UNAVAILABLE when required verification cannot be performed. No criterion is PASS without proof, and N/A cannot waive a required check.

**If a criterion fails and repair is feasible** → enter iteration (Phase 6 rules apply).
**If all applicable criteria pass, with justified N/A where appropriate** → proceed to critique (Phase 6).
**If required verification is unavailable** → finish independent authorized work, then report bounded results and remaining gaps; do not repeat code changes to satisfy a missing environment or claim full verification.

**Output**: Scorecard with status per criterion, evidence or the specific limitation

## Phase 6: CRITIQUE — Pressure-Test Before Declaring Done

**Goal**: Challenge the fix before the user relies on it.

1. **Seek independent critique when available** (on Claude Code, the bundled `fix-critique` agent) with:
   - The symptom
   - The causal tree from investigation (confirmed branch path + pruned branches)
   - The fix (what was changed)
   - The verification evidence
If independent execution is unavailable, mark critique UNAVAILABLE and disclose the gap; self-review is not independent approval.

2. **Evaluate the actual verdict**:
   - **APPROVED** → proceed to REPORT
   - **CHALLENGED** → the concerns become input for the next iteration. Route back to INVESTIGATE with the specific challenges as new investigation targets

The critique agent checks 5 things:
- Root cause vs symptom fix
- Symptom coverage (similar bugs elsewhere)
- Regression risk
- Evidence verification
- Causal tree consistency

## Phase 7: REPORT — Transparent Status

**Goal**: Clear, honest summary. No overclaiming.

### Transparency Markers

Every item in the report gets one marker:

- **✅ Verified**: Checked with evidence (test output, reproduction, command results)
- **⚠️ Assumed**: Believed to be true based on reasoning, but not verified with a test
- **❓ Unknown**: Not checked at all — explicitly acknowledged gaps

### Report Contents

1. **Verdict**: Fixed within scope when all applicable criteria pass, any N/A is justified, and actual independent critique approves. If critique is unavailable, report the verified behavioral scope and review gap. Report partial verification when required evidence is unavailable; report unresolved when failures remain or the iteration limit is reached. Neither partial nor unresolved means fully verified.
2. **Root Cause**: The identified cause with evidence level
3. **Causal Tree**: The investigation path — confirmed branches, pruned branches with rejection evidence, any multi-causal findings
4. **Fix Applied**: What was changed, with rationale
5. **Scorecard**: Final status per criterion with evidence or a justified N/A/UNAVAILABLE reason
6. **Research Used**: What was searched externally, what was found, what sources
7. **Iteration History** (if >1 iteration): What was tried, what failed, what changed between iterations
8. **Remaining Gaps**: Anything marked ⚠️ or ❓

### After Reporting

- **Before any memory write**, follow [debugging-memory storage preconditions](../debugging-memory/SKILL.md): confirm task authorization and inspect `status` for the actual server working directory and configured memory path. They must match the authorized project or an explicitly selected shared corpus; otherwise keep a task report and disclose the storage gap.
- **Store the incident only after those checks pass** via the existing debugger `store` fields and narrative for future retrieval
- **Record an outcome only after those checks pass and a retrieved repair was actually attempted**, using `worked`, `failed` or `modified`. Keep uncertain results in the incident narrative or task report; do not invent an outcome enum.
- **Write state only when task-authorized** to `.claude-code-debugger/debug-loop/scorecard.md`

## Iteration Rules

When any criterion fails or the critique is CHALLENGED, iterate:

1. **Diagnose why the criterion failed** — don't blind retry
2. **Revise the hypothesis** if verification disproved it
3. **Create a targeted fix plan** for the failed mechanism and affected criteria
4. **Execute fix**
5. **Re-verify failed and affected checks** — rerun previously passing checks whose evidence the new change can invalidate. Retain unrelated passing evidence only when its source and assumptions remain applicable.
6. **Re-score and re-critique**

Use [review feedback](../code-principles/references/review-feedback.md) to reconcile repeated critique findings, changed closure premises and affected caller contracts. One justified budget covers nested review and repair; the five-iteration maximum below still applies. Record failed hypotheses and evidence in [incident lessons](../code-principles/references/incident-learning.md) when authorized.

### Convergence Detection

Load `references/convergence-rules.md` for detailed rules and escalation templates.

Summary:
- **Same hypothesis fails 2x** → reject or revise it and seek discriminating evidence; ask only for genuinely missing context or a consequential user decision
- **Fix A breaks criterion B (oscillation)** → inspect shared ownership or conflicting requirements; continue an authorized adequate repair, asking only if requirements cannot be resolved
- **3+ criteria fail after a fix** → systemic issue, stop loop and reassess the approach entirely
- **New regression detected** → fix is causing side effects, reconsider the approach
- **Hard stop at 5 iterations** → report what's known and what isn't. Never silently loop beyond 5

## Anti-Patterns to Avoid

| Anti-Pattern | What to Do Instead |
|-------------|-------------------|
| Accepting the first explanation | Branch first — identify 2+ plausible causes before pursuing any |
| Fixing the symptom | Trace to root cause, fix there |
| "This should fix it" | Run the tests, show the output |
| Retrying the same approach | If it failed once with the same evidence, it'll fail again. Change the hypothesis |
| Declaring victory without evidence | Every claim needs a ✅/⚠️/❓ marker |
| Skipping research when stuck | If you don't know why something behaves this way, search for it |
| Hiding uncertainty | ⚠️ and ❓ are not failures — they're honest. Hiding them is the failure |

# Audit methods: what to run, when, and how to adapt

Reading rules does not change what a reviewer finds; running a check does. This file names the checks. `<cp>` is the absolute path of the plugin's `skills/code-principles` folder (resolve symlinks). Every command here only reads the audited repo. Put scripts, packets and logs in a scratch folder outside it, never import or run the repo's own code unless execution is authorized, and skip `dist/`, generated, vendored and fixture paths.

**Output of any recipe or scan is candidates, never findings.** A candidate becomes a finding only after the verification in section 5.

## 1. Recon (one step, about 30 s)

Run `python3 <cp>/scripts/recon.py <root> [--base REV | --paths FILE...]`. It prints the signals below and the starting route as JSON. Without it, collect them by hand:

- `files`: `git ls-files | wc -l`, or the changed-path count for a diff.
- `languages`, `multi_lang`: extension counts; `multi_lang` when ≥2 languages each hold >10% of files.
- `scope`: `diff` (paths or `git diff --name-only BASE`) or `repo`; `diff_modules` = distinct top-level folders touched.
- `services`: separate roots holding a manifest, Dockerfile or deploy config.
- `io_conc`: files with append/rename/lock/flock/O_APPEND/appendFile/writeln!/spawn/create_task/Promise.all/asyncio.gather.
- `retry`: files with retry/backoff/timeout/deadline/retryable.
- `serial`: files with json.dumps/JSON.stringify/serde/pydantic/zod/schema.

## 2. Starting route

| Signals | Generate candidates with | Lanes | Who verifies |
|---|---|---|---|
| `diff`, ≤10 files, 1 module | `scan.py <changed files>`; callers of each changed public symbol; R1 if literals or config changed, R4 if `serial`, R5a if `io_conc`, R5b if `retry` | none | lead |
| `diff`, ≥3 modules or >10 files | as above, plus `architect impact <file>::<symbol>` per changed public symbol to pull in unchanged callers | one per module only if the modules share no changed contract; otherwise one agent | each lane its own; lead re-verifies cross-lane findings |
| `repo`, <200 files, 1 language | `scan.py .`, R1, R2, R3; R4/R5a/R5b when their signal is present | none | lead |
| `repo`, ≥200 files or `multi_lang` | Phase A by dimension, repo-wide: lane F (`scan.py` F rules + R1), lane N (R2 + R4), lane S (R3 + hop count), lane E (R5a/R5b when signalled). Never split a cross-cutting class by module. | Phase B by module (`campaign.py batch`): read the module for checklist A–D and check the Phase A candidates that land in it | module lane, never the lane that generated the candidate |
| `services` ≥2 | add R4 across each service boundary; NavGator `connections`/`trace` only if `.navgator/` already exists (its scan writes into the repo, so ask first) | add one contract lane | both sides cited |
| a tool is missing | use the next method for that dimension (LSP → `architect` → import grep) or mark the cell `UNAVAILABLE` | — | — |

Callers: `rosslabs-lsp refs --symbol <name> --path <root>`; when it reports `ready: false`, use `architect impact` or `rg -nw <name>`. Brief every lane with the lane section of [reviewer role](../../audit/references/reviewer-role.md#lane-briefs).

## 3. Recipes

Each recipe prints `file:line` plus the question the reviewer must answer at that site. Answer the question by reading the site; the hit alone proves nothing. Use `rg` where it exists, else `git grep -nE` with the same pattern.

**R1 — literals that copy a source of truth.** Harvest the owned values: manifest versions (`package.json`, `pyproject.toml`, `Cargo.toml`, plugin manifests), config keys, env-var names (`process.env.X`, `os.environ["X"]`, `getenv("X")`). For each value, list literal copies outside its owner file: `rg -nF '"<value>"' -g '!<owner>' -g '!**/dist/**'`. Question: *does this copy follow its source when the source changes, and in which context does it break?*

**R2 — naming and wire-key variants.** Collect quoted wire keys (not every identifier), normalize each by splitting camel/snake/kebab and lowercasing, group, and print groups with ≥2 spellings. Question: *do producer and consumer use the same spelling for the same field?* Identifier-level grouping is mostly legitimate Type/instance and language-convention pairs; stay at wire-key granularity.

**R3 — structure nodes.** `architect scan <root> --out <scratch>/arch`, then from `graph.json` count `calls` edges per function: hubs (top fan-in), entry points (fan-in 0, fan-out >0), pass-throughs (fan-in 1, fan-out 1). Exclude test files. Hubs are reading order for shared state and contracts; pass-throughs are reading order for checklist G1–G3, not findings (pass-through detectors measured about 20% precision). Question: *what capability does this layer add, and how many hops does the request take?*

**R4 — contract field diff.** For a producer/consumer pair (paired by message or type name, file name or an R2 group), list keys the producer writes (`json.dumps({...})`, struct fields, `JSON.stringify({...})`, schema fields) and keys the consumer reads (`.get("k")`, `["k"]`, `.k`, destructuring). Print consumer-reads minus producer-writes and the reverse. Question: *which side owns the contract, and is the missing field optional by that contract?*

**R5a — effect sites (concurrency, atomic writes).** `rg -n "open\([^)]*['\"]a|O_APPEND|appendFile|writeln!|write_all|\.rename\(|os\.replace|flock|lockf|Lock\(|tmp|temp"` in scope. Per site: *is the record written in one call? is a lock held across read-modify-write? is the temp name unique per call or only per clock tick? who else writes this path?*

**R5b — error classification (failure, retry, timeout).** `rg -n "retryable|Timeout|timed out|ETIMEDOUT|except .*Timeout|catch|status\s*=\s*\W?(failed|error|ok)"` in scope. Per site: *could the effect have completed before this branch ran? which status does the code report then? who retries, and is the effect idempotent?*

**R6:<slug> — class sweep.** Written mid-audit from a confirmed finding (section 4): the smallest regex or AST query matching the finding's site shape, run repo-wide. Name it `R6:<slug>`, e.g. `R6:two-write-append`, and keep the script beside the audit output.

## 4. Adapt during the audit

The starting route is a plan. After each recipe or lane returns, apply the first matching row and record what you did.

| Trigger | Do | Record |
|---|---|---|
| A confirmed finding whose mechanism is a class (non-atomic append, timeout reported as failure, copied version) | Write R6 for its site shape and run it on the whole repo, not just the current module. | sweep command, hits, confirmed |
| A repo convention seen while reading (own config loader, env accessor, lock or atomic-write helper) | Grep for sites that bypass it, e.g. `open(..., "a")` where `locked_append` exists. | convention, grep, hits |
| A planned method does not apply (LSP `ready: false`, architect parse gaps, no manifests) | Swap to the next method for that dimension, or mark the cell not covered. | method dropped and why |
| More than ~30 hits with fewer than ~1 in 5 confirmed on a 10-hit sample | Narrow once by repo convention (exclude tests/fixtures, restrict to wire keys). Still noisy: stop and report the dimension as low precision. | sample size, confirmed |
| Budget or time runs out | Stop and fill the coverage matrix with what remains uncovered. | matrix |

## 5. Verify each candidate

1. **Control the instrument first.** Before reporting a count, a "none found" or a hit, run the same grep or script on a known positive (a planted line or a site you already confirmed) and check its exit status. Never infer absence from truncated output, an errored glob or a pipe's exit code. Run `scan.py --self-test` before trusting a scan in a new environment.
2. Read the site and its callers (`rosslabs-lsp refs` or `architect impact`).
3. Name the source of truth or the violated contract. If you cannot name one, drop the candidate.
4. Look for counterevidence: an existing lock, a reader that tolerates the field, a test asserting the behavior, a documented policy constant.
5. **Probe when execution is authorized.** Write the cheapest discriminating check outside the repo (two processes appending to one file, comparing two version values, calling the classifier with a timeout raised after delivery) and keep its output. Label every finding `probed` (a check you ran confirmed it) or `read` (source reading only).
6. Re-open every cited line, yours and every lane's (`sed -n '<line>p' <file>`), before reporting. Reject a citation that lands on a comment or a different statement.
7. Log the outcome (section 7) under the checklist id or the recipe id that produced the candidate.

## 6. Coverage matrix

End the report with one table: rows are modules (or `repo-wide`), columns are the dimensions frozen, naming, structure, efficiency, failure/retry, concurrency, contract. Each cell uses the report vocabulary:

- `PASS (method)` — covered by the named method, no finding; `FAIL (ids)` — covered, findings listed by id.
- `N/A (reason)` — the dimension does not apply here.
- `UNAVAILABLE (missing tool or input)` — not covered, and why.
- Append `low precision n/N` when the noise rule in section 4 stopped the method.

State what was searched and what was not. A blank or missing cell is not coverage.

## 7. Tool commands, repair and logging

1. **Scan.** `python3 <cp>/scripts/scan.py <path> [<path>...]` lists signals by checklist section with `file:line`. Point it at the changed files or the operation under review, and at code you are about to write. A hit is a place to look; the main path still needs reading when there are no hits.
2. **Trace the operation, then read the hits.** Follow its entry point, helpers, callers and observable boundaries. Count how many times each input is fetched, parsed, queried or scanned per operation. Read the matching section of the [focused checklist](../../code-principles/references/focused-checklist.md).
3. **Repair (only when authorized) at the simplest adequate boundary.** Compare a symptom patch with a repair at the existing common owner; see [whole-system repair](../../code-principles/references/whole-system-repair.md). Remove work before adding caches, concurrency or layers. A fast path must pass the [contract gate](../../code-principles/references/focused-checklist.md#d-contract-gate--must-pass-before-any-fast-path-ships).
4. **Verify with the repo's tools.** Run the original case and the relevant tests. A fix counts as verified only when its test fails on the pre-fix code or on a one-line mutant; see [review feedback](../../code-principles/references/review-feedback.md#verify-the-recommendation-and-the-oracle). For a speed claim, time the same workload before and after on the same machine in the same session.
5. **Log.** `python3 <cp>/scripts/outcome.py add --repo <abs repo> --item <id> --where <file:line> --decision <fixed|accepted|kept|rejected> [--gain "-27% p50"] [--log-file <path outside the repo>]`. `<id>` is a checklist id (`B7`, `F3`) or the recipe id (`R1`…`R5b`, `R6:<slug>`) that produced the candidate. Do not invent an id; keep findings without one in the report only. Decisions: `fixed` changed and verified, `accepted` real and not yet fixed, `kept` real tradeoff where the current code is right, `rejected` not a real issue. Without `--log-file` the log goes to `<repo>/.code-principles/outcomes.jsonl`, so a read-only review must pass `--log-file`. `outcome.py score` shows each id's hit rate.

## 8. Self-update: from recipe to rule

A method that keeps finding real defects should become a rule; one that stops should go. Follow build-loop's experimental → promotion pattern (`build-loop/skills/self-improve/SKILL.md`, promotion-reviewer agent); do not build a new store.

1. **Capture.** Log every recipe, sweep and convention grep that produced a confirmed finding with `outcome.py add --item <recipe id>`; keep the script beside the audit output.
2. **Candidate.** `outcome.py candidates --min-repos 2` lists recipe ids with confirmed outcomes (`fixed`, `accepted` or `kept`) on at least 2 distinct repos; pass every log with `--repo` or `--log-file`.
3. **Experimental rule.** Implement the candidate behind `scan.py --experimental`; nothing enters the default scan at this stage.
4. **Measure precision.** Use the section F method: run on the pinned public repos, sample and label hits, and record them in a `*-precision.json` like [frozen-values-precision.json](../../code-principles/references/frozen-values-precision.json). Keep only at precision ≥ ~0.7 on ≥8 labelled hits; record a cut with its number.
5. **Pre-registered eval.** Commit the decision rule first, then test on cases mined after the rule froze. Wins on cases known while writing the rule do not count.
6. **Promote.** build-loop's promotion-reviewer agent gives a verdict; the owner approves the move into the default scanner or checklist. Neither step is automatic.
7. **Retire.** A rule or recipe whose `outcome.py score` hit rate falls below the keep threshold over a rolling window is flagged for removal.
