# Focused code review

Review the requested operation against its explicit contract. Inspect changed code and affected callers, state owners, registration and failure paths. Use source evidence, not a checklist hit alone, to confirm a trigger, cause and consequence. Consider counterevidence and intentional behavior; clean code needs no finding. Missing a preferred technique alone is not a defect.

A value frozen in code is a candidate defect when it has a live source of truth (manifest, config, environment, database, API or a sibling constant) or varies by machine, deployment, tenant or date. Confirm it by comparing, not by reading one file: for each version string, path, host, id, accepted-values set, spelling or name table, regex that mirrors a table, and list copied from another component, look in every supplied file for its source (package and plugin manifests, serializer attributes such as rename rules, the table or constant it mirrors, the other program or API it describes) and compare value by value. A mismatch, or a copy that will not follow its source when the source changes, is the finding; name the context in which the copy breaks. Real protocol and policy constants stay, and a value that looks wrong may be newer than your knowledge. A layer, wrapper, factory, second state owner or service split is a candidate defect when it adds a failure point or a copy of state and no named capability.

Trace the simplest adequate correction across affected paths. Preserve output semantics, ordering, error contracts, supported consumers, operation identity, retry ownership, deadlines and recovery behavior. An error handler is defective when it loses required behavior or hides incomplete work; an intentional terminal or best-effort handler can be valid. Sequential work and fixed limits can be intentional. Only claim measured performance gains from actual comparable measurements.

For cleanup, check dynamic registrations, external consumers, flag prerequisite edges and emergency paths before calling code unused. Absence in sampled telemetry is not proof of disuse. Remove only behavior the supplied contract permits removing.

Keep severity separate from introduced/pre-existing origin. Reconcile prior findings: suppress unchanged resolved issues; reopen the same identity or explicitly link it when a closure premise changes. Cover unchanged callers affected by a changed contract. Group instances of one cause; do not invent nits or duplicates.

Historical memory offers hypotheses. Check applicability, invalidation and failed approaches before reuse; no retrieval score proves current causality. Missing tools or skipped inputs are coverage gaps, not clean reviews. Do not write incidents or repair code during review-only work. In an authorized repair, reproduce when feasible, correct the cause and verify affected guarantees. Distinguish proposed checks, executed tests, runtime and deployment.

Return material findings with trigger, causal explanation, location, consequence, smallest adequate action and discriminating verification. Report no material findings when supported. Do not fabricate execution or certainty.

# Debug with shared audit principles

```text
identify symptoms, expected behavior, revision and authorized scope
if memory available: search symptoms and inspect candidate context
reproduce when feasible; record original-environment gaps
trace plausible causes through shared state and failure boundaries
predict a check that distinguishes the strongest cause from alternatives
record failed approaches; check the oracle enforces the actual contract
compare the symptom patch with the simplest adequate mechanism repair
repair in scope; run the prediction, reproducer and affected regressions
seek independent critique when available; disclose its actual status
report evidence and gaps
if incident recording authorized: follow debugging-memory/SKILL.md storage checks
```

For a review-only request, investigate and report proposed repairs without applying code changes, writing workflow state or storing incidents unless separately authorized.

Load [shared principles](../code-principles/SKILL.md) and relevant challenge references. For a recurrent, disputed or nontrivial cause follow [the deeper loop](../debug-loop/SKILL.md). For an obvious cause use a short investigate, fix, verify sequence. A past KNOWN_FIX still requires validation against current contracts and verification.

The bundled MCP server `code-audit-debugger` supplies search, detail, store, outcome, status, list, patterns and read_logs. Use actual host-exposed names. If unavailable, report that memory was not checked and continue with source/log/test evidence. Never invent matches or successful storage. Do not write another host's personal assistant memory.

The procedure is host-neutral. On Claude Code the bundled agents (`assessment-orchestrator` and four domain assessors, `root-cause-investigator`, `fix-critique`) provide parallel domain assessment, causal-tree investigation and critique; see [debugging memory](../debugging-memory/SKILL.md#independent-work). Investigate directly when a host lacks agent registration. Independent critique requires an actual independent execution; self-review cannot substitute for it. If unavailable, mark critique UNAVAILABLE and deliver bounded results with that gap disclosed.

Before any incident or outcome write, follow [debugging memory](../debugging-memory/SKILL.md): check `status` and require its actual working directory and configured memory path to match the authorized project or explicitly selected shared corpus. If the destination cannot be established, keep a task report and disclose the storage gap.

Use [review feedback](../code-principles/references/review-feedback.md) for critique/re-review and [incident learning](../code-principles/references/incident-learning.md) for historical outcomes. Share one justified budget across review and repair; do not reset the iteration limit when switching workflows.

Timeouts can leave completed writes behind. Preserve logical identity, reconcile uncertain effects, retry at one layer, choose limits from relevant observations or explicit reasonable assumptions, and propagate the total deadline. Increasing a timeout alone does not prevent duplicate effects.

# Debug Loop — Iterative Root Cause Debugging

A 7-phase debugging loop: investigate via causal tree analysis, hypothesize root cause, implement targeted fix, verify with evidence, score against criteria, pressure-test via critique agent, and report with transparency markers. Iterates up to 5x on failures.

Read [shared principles](../code-principles/SKILL.md) and relevant challenge details before choosing a repair.

## Scope Check

Before entering the loop, assess whether it's warranted. Choose depth from the actual causal uncertainty, recurrence and scope. Retrieval similarity is not calibrated confidence in a fix.

- **Skip the deep loop** for `KNOWN_FIX` only after validating causal fit and current contracts; adapt and verify
- **Skip the loop** for trivial issues: typos, missing imports, obvious config errors where the cause is immediately clear
- **Enter the loop** for a nontrivial or disputed cause, a previous repair that did not hold, an unexplained cross-component failure, or an explicit deep-investigation request. A weak or absent memory match is one input, not an automatic trigger.

## Efficiency

- Terminal output: current phase, key findings (one line each), status changes, failures. No verbose reasoning
- Agent context: minimum needed per job. Pass symptom + relevant findings, not full conversation history
- Load convergence rules reference on demand only when entering iteration

For a repair or restart crossing component boundaries, read [change and failure isolation](references/change-isolation.md). Verify the shared cause and affected callers; a past incident or a small diff does not establish that the current boundary is adequate.

## Phase 1: INVESTIGATE — Gather Evidence and Trace Root Cause

**Goal**: Understand what's actually failing and why, not just what it looks like.

1. **Search memory when available** — use the bundled debugger search tool; inspect candidate context. If unavailable, disclose the gap and continue source investigation.
2. **Reproduce the issue when feasible** — identify exact steps, commands, or conditions that trigger the bug. If the original environment is unavailable, record the causal evidence and limits; distinguish a controlled regression case from reproduction of the original incident.
3. **Trace plausible causes** — inspect callers, state and failure boundaries, rank by evidence and prune with counterevidence. Use an independent investigator only when authorized and available (on Claude Code, the bundled `root-cause-investigator` agent; for an unclear multi-domain symptom, `assessment-orchestrator` and its domain assessors); agent registration is not required for investigation.
4. **Research gate** — if the investigator flags unfamiliar error codes, library behavior, or version-specific issues:
   - Search official sources using a minimal non-sensitive query; never send private code, credentials or logs without authorization
   - Document what was searched and what was found
   - If search is unavailable, document what SHOULD be searched
5. **Assess completeness** — does the investigation explain ALL reported symptoms? Check for multi-causal bugs (2+ independent root causes)

**Output**: Causal tree (with confirmed and pruned branches), reproduction steps, evidence gathered, research performed

## Phase 2: HYPOTHESIZE — State the Root Cause

**Goal**: Commit to a specific, testable hypothesis before writing any fix.

1. **State the root cause hypothesis** with evidence level:
   - **Strong**: Multiple evidence types (code, logs, reproduction) all point to this cause
   - **Moderate**: Some direct evidence plus reasonable inference
   - **Weak**: Mostly inference, limited direct evidence — consider investigating other branches first
2. **Predict verification test**: If this hypothesis is correct, what specific test would prove it?
3. **Predict related symptoms**: What else should be affected if this root cause is real?
4. **If multiple hypotheses exist**, rank by evidence strength. Pursue the strongest first

**Output**: Hypothesis statement, evidence level, prediction test, related symptom predictions

## Phase 3: FIX — Implement Targeted Change

Apply code changes only when the task authorizes repair. For review-only requests, report the supported cause, proposed correction and verification plan; do not apply fixes or write incident/workflow state.

**Goal**: Make the simplest adequate change that addresses the causal mechanism across affected supported paths.

1. **Compare a symptom patch with a causal repair** — trace the existing state owner and affected callers before adding a case-specific exception. A null guard can be correct at a boundary that permits missing data; establish the contract rather than treating every guard as a symptom patch.
2. **Keep changes proportional** — repair the shared mechanism where needed, preserving supported callers and valid counterexamples. Avoid unrelated cleanup or speculative frameworks; minimum adequate means causal coverage, not the fewest changed lines.
3. **Note exactly what was changed and why** — this becomes the evidence trail

**Output**: List of changes with rationale

## Phase 4: VERIFY — Test the Fix with Evidence

**Goal**: Collect concrete evidence that the fix works.

1. **Run the prediction test** from Phase 2 — does it confirm the hypothesis?
2. **Run the original reproduction steps** — is the symptom gone?
3. **Run related test suite** — do existing tests still pass?
4. **Check for regressions** — run broader test suite if available
5. **Verify related symptom predictions** — are the predicted effects present?

Each applicable verification step needs evidence: command output, test results, or observable behavior. Mark a genuinely inapplicable check N/A with its scope reason, or a missing required environment/check UNAVAILABLE with the gap. Neither is PASS. "It should work" is not evidence.

**Output**: Evidence for each verification step

## Phase 5: SCORE — Evaluate Against Criteria

**Goal**: Evidence-based status for each criterion.

Score against these criteria:

| # | Criterion | Method | Pass Condition | Evidence Required |
|---|-----------|--------|----------------|-------------------|
| 1 | Symptom resolved | Reproduction steps | Symptom no longer occurs | Command output or test result |
| 2 | Tests pass | Test suite | All relevant tests pass | Test runner output |
| 3 | No regressions | Broader test suite | No new failures introduced | Test runner output |
| 4 | Root cause addressed | Code review | Fix targets root cause, not symptom | Diff + reasoning |
| 5 | Hypothesis confirmed | Prediction test | Prediction test passes | Test output |

**Every criterion needs an evidence status.** Use PASS with observed evidence, FAIL for an observed unmet criterion, N/A only when genuinely inapplicable to the approved scope, and UNAVAILABLE when required verification cannot be performed. No criterion is PASS without proof, and N/A cannot waive a required check.

**If a criterion fails and repair is feasible** → enter iteration (Phase 6 rules apply).
**If all applicable criteria pass, with justified N/A where appropriate** → proceed to critique (Phase 6).
**If required verification is unavailable** → finish independent authorized work, then report bounded results and remaining gaps; do not repeat code changes to satisfy a missing environment or claim full verification.

**Output**: Scorecard with status per criterion, evidence or the specific limitation

## Phase 6: CRITIQUE — Pressure-Test Before Declaring Done

**Goal**: Challenge the fix before the user relies on it.

1. **Seek independent critique when available** (on Claude Code, the bundled `fix-critique` agent) with:
   - The symptom
   - The causal tree from investigation (confirmed branch path + pruned branches)
   - The fix (what was changed)
   - The verification evidence
If independent execution is unavailable, mark critique UNAVAILABLE and disclose the gap; self-review is not independent approval.

2. **Evaluate the actual verdict**:
   - **APPROVED** → proceed to REPORT
   - **CHALLENGED** → the concerns become input for the next iteration. Route back to INVESTIGATE with the specific challenges as new investigation targets

The critique agent checks 5 things:
- Root cause vs symptom fix
- Symptom coverage (similar bugs elsewhere)
- Regression risk
- Evidence verification
- Causal tree consistency

## Phase 7: REPORT — Transparent Status

**Goal**: Clear, honest summary. No overclaiming.

### Transparency Markers

Every item in the report gets one marker:

- **✅ Verified**: Checked with evidence (test output, reproduction, command results)
- **⚠️ Assumed**: Believed to be true based on reasoning, but not verified with a test
- **❓ Unknown**: Not checked at all — explicitly acknowledged gaps

### Report Contents

1. **Verdict**: Fixed within scope when all applicable criteria pass, any N/A is justified, and actual independent critique approves. If critique is unavailable, report the verified behavioral scope and review gap. Report partial verification when required evidence is unavailable; report unresolved when failures remain or the iteration limit is reached. Neither partial nor unresolved means fully verified.
2. **Root Cause**: The identified cause with evidence level
3. **Causal Tree**: The investigation path — confirmed branches, pruned branches with rejection evidence, any multi-causal findings
4. **Fix Applied**: What was changed, with rationale
5. **Scorecard**: Final status per criterion with evidence or a justified N/A/UNAVAILABLE reason
6. **Research Used**: What was searched externally, what was found, what sources
7. **Iteration History** (if >1 iteration): What was tried, what failed, what changed between iterations
8. **Remaining Gaps**: Anything marked ⚠️ or ❓

### After Reporting

- **Before any memory write**, follow [debugging-memory storage preconditions](../debugging-memory/SKILL.md): confirm task authorization and inspect `status` for the actual server working directory and configured memory path. They must match the authorized project or an explicitly selected shared corpus; otherwise keep a task report and disclose the storage gap.
- **Store the incident only after those checks pass** via the existing debugger `store` fields and narrative for future retrieval
- **Record an outcome only after those checks pass and a retrieved repair was actually attempted**, using `worked`, `failed` or `modified`. Keep uncertain results in the incident narrative or task report; do not invent an outcome enum.
- **Write state only when task-authorized** to `.claude-code-debugger/debug-loop/scorecard.md`

## Iteration Rules

When any criterion fails or the critique is CHALLENGED, iterate:

1. **Diagnose why the criterion failed** — don't blind retry
2. **Revise the hypothesis** if verification disproved it
3. **Create a targeted fix plan** for the failed mechanism and affected criteria
4. **Execute fix**
5. **Re-verify failed and affected checks** — rerun previously passing checks whose evidence the new change can invalidate. Retain unrelated passing evidence only when its source and assumptions remain applicable.
6. **Re-score and re-critique**

Use [review feedback](../code-principles/references/review-feedback.md) to reconcile repeated critique findings, changed closure premises and affected caller contracts. One justified budget covers nested review and repair; the five-iteration maximum below still applies. Record failed hypotheses and evidence in [incident lessons](../code-principles/references/incident-learning.md) when authorized.

### Convergence Detection

Load `references/convergence-rules.md` for detailed rules and escalation templates.

Summary:
- **Same hypothesis fails 2x** → reject or revise it and seek discriminating evidence; ask only for genuinely missing context or a consequential user decision
- **Fix A breaks criterion B (oscillation)** → inspect shared ownership or conflicting requirements; continue an authorized adequate repair, asking only if requirements cannot be resolved
- **3+ criteria fail after a fix** → systemic issue, stop loop and reassess the approach entirely
- **New regression detected** → fix is causing side effects, reconsider the approach
- **Hard stop at 5 iterations** → report what's known and what isn't. Never silently loop beyond 5

## Anti-Patterns to Avoid

| Anti-Pattern | What to Do Instead |
|-------------|-------------------|
| Accepting the first explanation | Branch first — identify 2+ plausible causes before pursuing any |
| Fixing the symptom | Trace to root cause, fix there |
| "This should fix it" | Run the tests, show the output |
| Retrying the same approach | If it failed once with the same evidence, it'll fail again. Change the hypothesis |
| Declaring victory without evidence | Every claim needs a ✅/⚠️/❓ marker |
| Skipping research when stuck | If you don't know why something behaves this way, search for it |
| Hiding uncertainty | ⚠️ and ❓ are not failures — they're honest. Hiding them is the failure |

# Focused engineering checklist

Load only sections relevant to the operation. Pattern matches are investigation leads; establish a violated contract and consequence before reporting a defect.

## A. Speed and efficiency

- **A1 Same input fetched or parsed twice.** Look for a fetch, read, `JSON.parse`, `cheerio.load`, `JSDOM`, `BeautifulSoup` or `json.loads` on the same data in two helpers. Parse once and pass the result.
- **A2 Work inside a loop that could be batched (N+1).** A query, HTTP call or file read inside a loop over earlier results. Batch, prefetch, or eager-load.
- **A3 Sequential awaits over independent items.** `for … { await … }` where items don't depend on each other. Run with *bounded* concurrency (see B5).
- **A4 Repeated scans as data grows.** Nested loops, `.find`/`in list` inside a loop, or re-scanning the input from the start on every match (e.g. `source.substring(0, match.index).split('\n')` to get a line number). Build a lookup or running offset once.
- **A5 Synchronous blocking work on a request or event-loop path.** `readFileSync`, `execSync`, `inflateSync`, large `XLSX.read`, CPU-heavy parsing. Move it off the hot path or into a worker; wrapping sync code in `p-limit`/`Promise.all` does not parallelize it.
- **A6 Doing unrequested work.** Loading subresources (`resources: 'usable'`), computing fields nobody reads, copying whole collections to read one item.
- **A7 Measure before a big change; don't skip known-cheap wins.** Find the critical code with a profiler before restructuring. Compare several input sizes when investigating growth, and prioritize the measured cost of the whole task; linear work can still dominate it. Picking the efficient option when it is equally simple is not premature optimization (Knuth's full quote).

## B. Scale and load

- **B1 Every queue, buffer and request-fed collection has a size limit and a rejection path.** `asyncio.Queue()` with no `maxsize`, an unbounded channel, a list/map that grows per request.
- **B2 Choose timeouts intentionally and propagate the operation deadline.** Base the value on relevant latency data or a stated reasonable assumption, including user expectations and cleanup/retry costs. A timeout's presence alone does not justify its value. Inspect `fetch` without `signal`/`AbortSignal.timeout` and `requests.get` without `timeout=`; use [timeout guidance](timeouts.md) when selecting or changing limits.
- **B3 Retry at one layer only, under a retry budget.** Don't wrap an SDK or HTTP client that already retries. Never retry a non-idempotent write without an idempotency key reused across attempts.
- **B4 Shed excess load early and cheaply.** Reject before expensive work (auth lookups, parsing, logging) when overloaded.
- **B5 Cap fan-out.** `Promise.all(items.map(call))` or `asyncio.gather(*…)` over unbounded input needs a limit. For wide fan-out, check the slowest 1% of whole requests, not the average.
- **B6 Caches are bounded, coalesced and expire.** A plain map used as a cache needs eviction, a TTL, one in-flight fetch per missing key, and a plan for cold start.
- **B7 Cap untrusted sizes.** Decompressed size (`maxOutputLength`), upload size before `arrayBuffer()`, file size before parsing.

## C. Failure handling

- **C1 Test every error handler.** Most catastrophic failures in large distributed systems come from mishandled errors the code already caught. Empty, log-only and `TODO` handlers are leads. Confirm a lost guarantee, hidden failure or invalid continuation; intentional terminal and best-effort handling can be correct.
- **C2 Handle a failure where something useful can be done; otherwise pass it up with context.** Don't catch broadly to continue with state you can't trust.
- **C3 A timeout is not proof nothing happened.** Reconcile uncertain writes before repeating them.
- **C4 Define what partial success leaves behind.** List each effect; publish only complete state or record what needs cleanup.
- **C5 Background work has an owner.** Every spawned task is awaited, cancelled or supervised; child failure cancels siblings when the parent needs all of them.
- **C6 Report what was skipped.** When code skips input it cannot read, decode, fit or access, count it and say so. A result of "nothing found" must never mean "didn't look". Check that files, rows or pages skipped by `except`/`continue` paths reach the summary.

## D. Contract gate — must pass before any fast path ships

- **D1 Empty, negative, zero and boundary inputs** behave exactly as before (compare old vs new on the same inputs).
- **D2 Output types and conversions are preserved,** not just values (e.g. library numeric types vs raw ints).
- **D3 Subclasses, alternate implementations and private storage** your fast path assumes are checked, or the fast path is guarded to the exact types it handles.
- **D4 Existing guards stay** unless removing them is required. A few-percent gain does not justify dropping a type or length check.
- **D5 Error types and messages callers rely on are unchanged.** Observable behavior is a contract even when undocumented (Hyrum's Law).
- **D6 Untrusted names never become paths.** `basename` plus a generated id; reject `..`.
- **D7 Untrusted URLs are checked where the connection is made.** Validate the resolved IP at connect time (or pin it), re-validate every redirect, and fetch once, passing the body on instead of letting a second component fetch again.

Write the comparison as a differential check: run old and new over the same inputs including D1–D3 cases and assert identical results.

## E. Structure and change hygiene

- **E1 Small, self-contained changes;** refactors separate from behavior changes.
- **E2 Total code size matters more than how it is split.** Split only when the whole operation gets easier to understand.
- **E3 Types catch some bugs, not most.** Use them for meanings that are easy to confuse (ids, units); still test behavior.
- **E4 Prefer real implementations, then fakes, then mocks** in tests; mock only at real system boundaries.
- **E5 Update or delete a comment in the same change that alters its code.**
- **E6 Replace in small steps** (strangler fig) rather than rewriting from scratch.
- **E7 Pin dependencies; read a dependency's code and transitive deps before adopting it.**
- **E8 Hand-written parsers of standard formats** (PDF, CSV, HTML, ZIP, dates, source code) need tests for escapes, nesting, string literals and encodings, or a maintained library. Regex over source code matches inside strings and comments unless it accounts for them.

## F. Frozen values that should be dynamic

A value is a lead when it has a live source of truth or varies by context but is frozen in code; a literal alone is not. Procedure, harm order and the scanner's measured precision: [frozen values and path length](frozen-values-and-path-length.md).

- **F1 No machine-specific absolute paths.** Home paths and checkout paths break on the next machine; derive them from the repo root, an argument or config.
- **F2 No environment-specific hosts in code.** `localhost`, ports, private IPs and preview-deploy hosts belong in config or env; a fallback after reading env must be safe where it applies.
- **F3 Don't copy the manifest version.** Read `__version__`, CLI `--version` and client/server info from the package manifest or generate them.
- **F4 Limits, timeouts and thresholds that differ by deployment come from config,** with the default justified (see B2).
- **F5 Model ids, prices, regions, account/project/tenant ids and dates have an owner.** Read the catalog, config or clock; check the live source before calling a recent-looking value wrong.
- **F6 Feature toggles read their flag.** A toggle fixed to a constant may be dead code, a hidden switch or a deliberate kill switch; check [removal evidence](removal-evidence.md) before calling it unused.
- **F7 One owner per shared identifier.** File names, schema ids, env-var names, wire names and URLs used by several modules or languages come from one definition, are generated from it, or are checked for drift.

## G. Path length and brittle structure

- **G1 Count the hops from request to outcome** and name the shortest correct path that meets the same requirements.
- **G2 Every layer names its capability:** isolation, independent scale or deploy (P29), a real alternative (P09), a real boundary seam, a stable contract, or a simpler whole operation (P13). Pass-through wrappers, single-implementation factories, speculative plugin systems, duplicate state owners and service splits without isolation or scale need are leads.
- **G3 Judge brittleness by failure points and coupling:** dropped fields at a serialization hop, two tie-break rules for one record set, partial updates between owners, version skew, retries at two layers. Taste is not a finding.

# P01 — Define what the software should do before coding

Before coding, clarify expected behavior with concrete examples whenever different interpretations could change the result.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Implement the intended behavior with avoidable ambiguity resolved.

Concrete examples expose incompatible interpretations while changing the design is still cheap.

## Context

**Source applicability:** Inputs, acceptance criteria, partial completion, or the caller's next action admit consequential alternative interpretations.

**Avoid:** The existing contract already answers the question, or the change is a small reversible adjustment whose outcome is obvious.

**Premises:**
- A material behavior choice remains unresolved.
- Clarifying it costs less than likely rework or a wrong result.

## Options and costs

### Reuse or prototype

When: Existing behavior is already defined, or the user need is still being discovered.

Action: Reuse the existing examples when behavior is known; prototype the task when the need is unknown.

Gain: Gets feedback without documenting assumptions as settled requirements.

Cost: Hidden assumptions may survive, and prototype behavior may need revision.

### Write concrete examples

When: Different interpretations of success, failure, or partial completion would produce different code.

Action: Write examples showing accepted inputs, rejected inputs, visible changes, and rules that must remain true.

Gain: Exposes disagreements before implementation makes them expensive to fix.

Cost: Examples must be updated when the intended behavior changes.

### Define an explicit contract

When: Several callers or costly side effects depend on exactly the same behavior.

Action: Specify normal outcomes, important edge cases, permitted effects, and checks at the public boundary.

Gain: Gives implementations and callers a shared definition of correct behavior.

Cost: Detailed specifications take time and can lock in an untested requirement.

## Examples

Example: A batch import must decide whether one invalid item rejects the batch or produces a partial result.

Counterexample: Correcting a misspelled button label does not justify inventing an application architecture brief.

## Adapt when assumptions change

- The main unknown is what users need, rather than how to implement an agreed behavior. Prototype and observe the task before freezing a detailed specification; preserve a clear experimental question.
- The behavior is now established and the change is purely presentational. Reuse the contract and perform the relevant rendered check; omit a new design document.

## Context-adapted validation probes

- A success example and a material failure example have unambiguous expected outcomes.
- The delivered behavior satisfies those outcomes at the relevant boundary.

# P02 — Make builds, checks, and releases repeatable

When a build, check, or delivery step must be repeated or handed off, make it reproducible and add automation only when its recurring benefit justifies maintenance.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Reproduce important changes, failures, and delivery operations reliably.

Versioned inputs, repeatable builds, and concrete defect evidence let different people or agents reproduce the same operation.

## Context

**Source applicability:** Changes recur, several contributors work on the product, setup knowledge is implicit, or a reported defect cannot be reproduced.

**Avoid:** A working repository workflow already supplies the needed evidence; do not create a competing build or tracking system for one task.

**Premises:**
- The artifact will be maintained, reproduced, or handed off.
- Automation will support a recurring operation rather than add an unused parallel process.

## Options and costs

### Follow documented steps

When: The operation is rare, short, and easy for another person to repeat.

Action: Record the inputs and steps, perform the check, and keep the result.

Gain: Makes the operation repeatable without maintaining automation.

Cost: People can omit steps or use different inputs.

### Script the repeated step

When: Setup or validation is repeated often enough that manual steps are being missed or performed differently.

Action: Reuse existing tools and automate the repeated step that causes errors or wasted effort.

Gain: Reduces variation without building a second delivery system.

Cost: Someone must maintain the script and its assumptions about the environment.

### Use an integrated pipeline

When: Several contributors repeatedly build, check, and deliver changes that others depend on.

Action: Connect the required build, verification, and delivery steps in the existing pipeline.

Gain: Runs the same checks consistently and catches omissions earlier.

Cost: The pipeline needs maintenance and can delay feedback or delivery when it fails.

## Examples

Example: A packaging fix must be reproducible outside the developer's configured machine.

Counterexample: Saving a uniquely named research document does not require constructing a CI pipeline or a new defect database.

## Adapt when assumptions change

- A one-off experiment becomes a maintained component. Add repeatable setup and checks before multiple consumers depend on it.
- An existing pipeline already covers the changed boundary. Run and reference it instead of building another pipeline or tracking surface.

## Context-adapted validation probes

- The intended build or check works from the documented starting state.
- Another contributor can reproduce a material defect or the evidence explains why it remains uncertain.

# P03 — Use safe defaults and ask users when their judgment is needed

When a workflow requires a choice, use a safe default for implementation details and ask the user when their preferences, judgment, or authority are necessary.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Let users complete tasks and make meaningful informed choices.

Task-based defaults and observed usability reduce unnecessary decisions and reveal whether users can complete the real workflow.

## Context

**Source applicability:** Users face technical options, confusing errors, invisible state, or a workflow whose success cannot be inferred from code alone.

**Avoid:** The choice expresses meaningful intent, has consequences only the user can judge, or requires the user's authority.

**Premises:**
- The system has enough information to choose safely, or a useful default can be reversed.
- The decision is an implementation detail rather than a material user preference or authorization.

## Options and costs

### Choose a safe default

When: The system can determine a safe implementation choice and the user can easily reverse it.

Action: Apply the default and provide a clear way to change or undo it.

Gain: Lets the user finish the task with fewer interruptions.

Cost: A wrong default can hide a consequence the user would have chosen differently.

### Offer optional controls

When: Most users can use the default, but some need to adjust the behavior.

Action: Provide a useful default and make additional controls available when needed.

Gain: Keeps the common task simple while allowing informed adjustments.

Cost: Users may not discover a control they need if it is hidden too deeply.

### Ask for a decision

When: The choice depends on the user's preferences, acceptable loss or cost, or authority.

Action: Explain the actual consequences and ask for the decision needed to proceed.

Gain: Preserves the user's control over outcomes the system cannot choose for them.

Cost: Adds a step; asking about implementation trivia creates unnecessary work.

## Examples

Example: An importer detects supported encodings automatically when detection is reliable and the user can preview the result.

Counterexample: The software must not infer that a user wants to discard conflicting records merely to avoid a dialog.

## Adapt when assumptions change

- A formerly internal choice now determines user-visible cost or data loss. Make that consequence explicit and obtain the required choice instead of silently applying the old default.
- The system can now determine a formerly technical choice reliably. Remove the unnecessary prompt while retaining a useful recovery or override path.

## Context-adapted validation probes

- A representative user can complete the task and understand the resulting state.
- The product does not silently choose a material preference or conceal an unresolved failure.

# P04 — Match design and testing effort to failure risk

Match engineering effort to the cost of failure and expected reuse, using the simplest approach that still meets the required correctness, recovery, and compatibility guarantees.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Meet required guarantees with proportionate engineering effort.

Spend effort where it reduces a consequential uncertainty or recurring cost, and preserve the ability to change cheap experiments.

## Context

**Source applicability:** Choosing test depth, abstraction, automation, or release scope under limited time.

**Avoid:** Do not use a deadline, prototype label, or confident code generation as a reason to waive known correctness or recovery requirements.

**Premises:**
- Failure consequences and expected reuse are sufficiently understood to choose a proportionate approach.
- The reduced scope still satisfies the user's required guarantees.

## Options and costs

### Run a limited experiment

When: The purpose is learning and the result can be discarded before others depend on it.

Action: Build the smallest experiment that answers the question and limit its exposure to users and data.

Gain: Produces early feedback with little long-term maintenance commitment.

Cost: The experiment may need substantial changes before it can support ongoing use.

### Build a focused solution

When: The required behavior is known and the change affects a small part of the system.

Action: Implement a simple solution and add safeguards for the failures that can actually occur.

Gain: Meets the current requirement without paying for speculative infrastructure.

Cost: Larger workloads or new requirements may require revisiting the design.

### Invest in stronger guarantees

When: Data loss, widespread disruption, or difficult recovery makes failure expensive.

Action: Add the recovery, isolation, compatibility, and verification needed for those consequences.

Gain: Reduces specific failure risks that a simpler implementation cannot adequately control.

Cost: Increases design time, delivery time, and continuing operating work.

## Examples

Example: Prototype a visual interaction quickly, then test durable selection logic once the interaction is chosen.

Counterexample: A time-limited release still needs duplicate-prevention guarantees if repeating a remote operation would harm users.

## Adapt when assumptions change

- The experiment now serves customers or stores persistent user data. Reassess validation, ownership, compatibility, and recovery before treating it as production infrastructure.
- The component is being discarded and its results are reproducible. Remove unnecessary generalization and long-term maintenance work while preserving truthful output.

## Context-adapted validation probes

- The selected work meets the required outcome.
- Deferred work has an explicit consequence and revisit trigger; limitations are not presented as completed guarantees.

# P05 — Estimate delivery dates from evidence and state the uncertainty

When planning delivery, investigate major unknowns and use comparable completed work where available, stating uncertainty instead of promising precision the evidence cannot support.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Plan delivery with an honest and relevant evidence basis.

Observed completion history and explicit assumptions constrain estimates and reveal when the comparison basis has changed.

## Context

**Source applicability:** Planning milestones, communicating delivery uncertainty, or deciding whether to reduce scope.

**Avoid:** Do not present a statistical confidence or precise date without a defensible basis; a trivial task need not acquire a scheduling system.

**Premises:**
- There is a real planning decision to inform.
- Past work is comparable enough to be useful, or the lack of comparability is disclosed.

## Options and costs

### Investigate before estimating

When: Unknown requirements or integration behavior prevent a defensible delivery estimate.

Action: Set a limited investigation milestone and identify what must be learned before forecasting delivery.

Gain: Replaces major guesses with evidence.

Cost: A reliable final delivery date remains unavailable until the investigation resolves enough uncertainty.

### Give a range and assumptions

When: Some work is understood, but there is little relevant history or important dependencies remain uncertain.

Action: Give a delivery range and state the dependencies and assumptions that could change it.

Gain: Supports planning without presenting uncertain work as a precise promise.

Cost: The range may be broad and depend heavily on judgment.

### Use comparable delivery history

When: Completed work is sufficiently similar in scope, tools, and integration demands.

Action: Use observed delivery times and distinguish implementation time from integration and release work.

Gain: Bases the forecast on actual variation in comparable work.

Cost: Old timing data can mislead after the team, tools, or kind of work changes.

## Examples

Example: A format migration estimate includes fixture collection and compatibility validation, not only serialization code.

Counterexample: An LLM's confidence in its next answer is not measured delivery history.

## Adapt when assumptions change

- New tooling makes implementation faster but integration work remains similar. Recalibrate those work categories separately rather than applying the implementation speedup to the entire schedule.
- The team, task class, or deployment process changes materially. Reduce reliance on old timing history until new comparable observations exist.

## Context-adapted validation probes

- The estimate covers the intended completion boundary.
- Observed misses update the estimate or its comparison class rather than being explained away.

# P06 — Make each value's meaning clear and prevent incorrect use

Give values specific names that communicate their meaning, units, and purpose, and use types and validation checks where needed to prevent values with different meanings from being used interchangeably.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Prevent wrong amounts, wrong record operations, wrong scheduled times, and reliance on unchecked input.

Explicit unit and ID names make a mix-up visible during review; types that enforce the distinction can reject the wrong argument, and entry checks can reject invalid external data.

## Context

**Source applicability:** The same number, string, or date representation can stand for different units, records, or time conventions, or external data has not yet been checked.

**Avoid:** Use names alone when a short local calculation makes the unit unambiguous and extra types would not prevent a plausible mistake. Checking one property, such as a nonempty ID, does not prove which customer it identifies.

**Premises:**
- A concrete mix-up is plausible: for example, a timeout in milliseconds may be passed to a function expecting seconds.
- Names, type checks, validation, and conversions enforce or expose the intended unit, ID kind, time convention, or input rule.

**Audit clarification:** ID and duration checks are examples. Select probes that reveal a consequential value-boundary mistake in the actual contract; local clear names can be sufficient.

## Options and costs

### Use clear names

When: A short local calculation uses one unit or one kind of ID, and a reviewer can inspect all its uses in one place.

Action: Name the value amountInCents, timeoutInSeconds, or customerId so its unit or purpose is visible at each use.

Gain: Makes unit and ID mistakes easier to spot without introducing new types.

Cost: Does not prevent passing amountInCents to a function expecting dollars; the parameter name and value still need to be checked.

### Use distinct types

When: Several functions pass similarly represented values, and a mix-up could change an amount, record, or scheduled time.

Action: Use types such as AmountInCents, CustomerId, OrderId, and UtcTimestamp, with explicit unit and time conversions.

Gain: Can reject passing OrderId to a function that expects CustomerId when those types are actually enforced.

Cost: Adds definitions and conversions; a type alias that still accepts any number or string does not prevent the mix-up.

### Check inputs before use

When: A form or API supplies unchecked data that must satisfy a specific rule, such as a nonnegative amount or a date in UTC.

Action: Parse the input, establish its unit or time convention, check the required range or format, and construct a checked value only after the checks pass.

Gain: Later code can rely on the property that was actually checked, such as amountInCents being nonnegative.

Cost: Requires a defined rejection path; a nonnegative amount can still use the wrong currency, and a well-formed ID can still identify the wrong record.

## Examples

Example: A timeout function expects seconds but receives 5000 milliseconds, so it waits 5000 seconds instead of 5 seconds unless the caller converts the unit.

Counterexample: A loop counter used only inside one short function rarely needs a separate class; an explicit unit in the name may suffice when no other unit enters the calculation.

## Adapt when assumptions change

- An amount or ID that used to come from internal code now arrives through a form or API. Establish its unit from the input contract and validate its format and allowed values before constructing the internal type; a type name is not proof that new input satisfies those rules.
- Text checked for one operation is now inserted into a different output context, such as an HTML page. Use the checks and output encoding required by that context; a length or ID-format check does not make the text safe to render as HTML.

## Context-adapted validation probes

- Try passing OrderId to an operation that expects CustomerId; confirm type checks reject it, or that clear names and checks expose the mismatch.
- Verify that converting 1000 milliseconds produces 1 second, and that storing and reading IDs or dates does not discard their kind, unit, or time convention.

## Research update (2026-10-14)

- Static type checkers (Flow, TypeScript) caught about 15% of 400 public JavaScript bugs. Types are a real but partial defense; keep behavior tests. — [Gao, Bird & Barr, To Type or Not to Type, ICSE 2017 (read via summary)](https://blog.acolyer.org/2017/09/19/to-type-or-not-to-type-quantifying-detectable-bugs-in-javascript)

## Values with a source of truth (2026-10-28)

A value's meaning includes where it comes from. A literal that has a live source of truth (manifest, config, environment, database, API, a sibling constant) or varies by machine, deployment, tenant or date is a mistaken-meaning risk in the same way as a mixed-up unit: the code states one value while the system means another. Name the source, find every copy and compare them, and read or generate the value from its owner. Real protocol and policy constants are correct. Procedure and scanner precision: [frozen values and path length](../../../code-principles/references/frozen-values-and-path-length.md).

# P07 — State the behavior and limitations callers must know

When wrapping a dependency, hide unnecessary machinery while explicitly preserving the timing, failure, consistency, and other guarantees that callers need to make correct decisions.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Give callers a simple contract that preserves required semantics.

A simple interface reduces routine knowledge while an explicit contract preserves the constraints callers must act on.

## Context

**Source applicability:** Wrapping a database, remote API, filesystem, UI subsystem, or replaceable mechanism.

**Avoid:** Do not promise locality, atomicity, freshness, or easy substitution merely because implementations share method signatures.

**Premises:**
- The boundary can state and enforce the guarantees it offers.
- Callers do not need all underlying details, but some semantics affect their behavior.

## Options and costs

### Use the dependency directly

When: The dependency already provides a simple contract that matches the required behavior.

Action: Call it directly and follow its documented timing, failure, and state guarantees.

Gain: Avoids an extra wrapper and a second set of concepts.

Cost: Callers depend on that implementation and may need changes when it changes.

### Wrap a focused capability

When: Callers benefit from hiding implementation details while retaining the guarantees they depend on.

Action: Expose a small interface and state its timing, errors, freshness, and consistency where these affect callers.

Gain: Reduces what callers must understand without hiding behavior that changes their decisions.

Cost: A misleading wrapper can make remote or non-atomic behavior look safer than it is.

### Expose different guarantees

When: Implementations differ in required behavior, such as ordering, freshness, or all-or-nothing updates.

Action: Expose the differing capabilities or use separate contracts instead of claiming the implementations are interchangeable.

Gain: Lets callers handle real limitations explicitly.

Cost: Callers must handle more variation and may need different execution paths.

## Examples

Example: A save contract exposes a version conflict rather than silently overwriting a concurrent update.

Counterexample: A generic storage adapter cannot make two databases interchangeable if one lacks a required transaction guarantee.

## Adapt when assumptions change

- A local operation becomes remote or eventually consistent. Revise timing, failure, freshness, and retry contracts; a source-compatible signature may no longer be behaviorally compatible.
- A dependency now guarantees an operation atomically. Simplify local scaffolding where that guarantee really covers the required effects; retain handling for effects outside its scope.

## Context-adapted validation probes

- Each implementation satisfies the same required semantics.
- Failures and performance at the real boundary match the caller's assumptions.

## Research update (2026-10-14)

- With enough users, someone depends on every observable behavior. Document or deliberately randomize observable incidentals such as ordering, timing and error text. — [Hyrum's Law](https://www.hyrumslaw.com/)

# P08 — Keep code together when it changes for the same reason

Separate code when its parts change for different reasons or owners, and keep it together when splitting would scatter one coherent rule.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Localize changes without scattering one coherent rule.

Cohesion keeps knowledge that changes together in one place and separates genuinely different change drivers.

## Context

**Source applicability:** A module mixes independently changing business rules, presentation, persistence, or external protocols.

**Avoid:** Do not equate one responsibility with one method, one statement, or a fixed file size.

**Premises:**
- The proposed responsibilities have different owners, rules, or change patterns.
- The split reduces coupling more than it adds navigation and coordination.

## Options and costs

### Keep one rule together

When: The operations change together and rely on the same rule and state.

Action: Keep the rule and its required state under one module or component.

Gain: Avoids spreading one change across several files and interfaces.

Cost: Unrelated responsibilities can accumulate if later changes are not reviewed.

### Separate an independent part

When: A mechanism, such as storage or formatting, changes independently of the surrounding business rule.

Action: Move that part behind a small interface while leaving the shared rule in one place.

Gain: Lets the independent part change with fewer edits to the business rule.

Cost: Adds an interface, more navigation, and mapping between the parts.

### Assign separate owners

When: Responsibilities have different owners, release needs, or patterns of change.

Action: Give each responsibility a clear module or component and define how they interact.

Gain: Supports independent changes and makes responsibility for defects clearer.

Cost: A split across code that must change together adds coordination without real independence.

## Examples

Example: Separate tax-policy calculation from a vendor-specific persistence mapping when they evolve independently.

Counterexample: Splitting each validation predicate into a separate class can scatter one coherent validation rule.

## Purpose and mechanism

Keep observable state within the operation's permitted guarantees.

Private preparation and a deliberate commitment boundary control which states become observable; reconciliation accounts for effects that cannot commit atomically.

## Context

**Source applicability:** An operation has several effects, publishes shared state, or can fail after making a persistent change.

**Avoid:** Do not add staging around a single operation already covered by a sufficient atomic guarantee, or assume resource cleanup reverses persistent effects.

**Premises:**
- The required invariant and observation boundary are identified.
- Atomicity, rollback, and compensation are claimed only for effects they actually cover.

### Use one all-or-nothing operation

When: One transaction or atomic primitive covers all changes that must succeed or fail together.

Gain: Provides all-or-nothing changes within the guarantee's actual scope.

Gain: Prevents readers from seeing incomplete preparation.

When: Required effects cannot all be included in one sufficient transaction.

Action: Record which effects completed, report partial status, and reconcile or compensate the remaining effects.

Gain: Provides accurate status and a deliberate path toward a consistent outcome.

Cost: Recovery is more complex, and compensation may not fully reverse an external effect.

- Inject or simulate a material failure between consequential steps.

# P19 — Retry failed requests only when another attempt can help safely

Retry a failed request only if the next attempt has a reasonable chance of succeeding and can be made without excessive load or harmful duplicate effects.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Improve resilience without unsafe repetition or uncontrolled retry load.

A stable operation identity or otherwise idempotent contract limits duplicate effects; bounded attempts, backoff, and jitter limit retry pressure.

## Context

**Source applicability:** A material operation encounters a retryable environmental failure and all repetition prerequisites are established.

**Avoid:** Do not automatically retry a non-idempotent write, a persistent rejection, an expired idempotency key, or an operation whose outcome is unknown without a reconciliation strategy.

**Premises:**
- The operation is safe to repeat under the actual provider contract.
- The cause is plausibly transient.
- The idempotency scope, payload rules, and retention window cover the intended retry.
- The retry fits the overall deadline and has a deliberate owner.

**Audit clarification:** Code, a proposed change, or a recovery claim decides whether to repeat or reconcile an operation after failure or uncertain completion. Unsafe or uncertain repetition remains relevant. Establish repeat-safety, expected usefulness, load, deadline, ownership, and actual provider guarantees. Missing prerequisites limit or reject repetition; they do not imply not_applicable.

## Options and costs

### Do not repeat yet

When: The failure will persist, or a write may already have completed and repetition could cause harm.

Action: Return the failure, correct the cause, or check the operation's status before deciding to repeat it.

Gain: Avoids harmful duplicate effects and requests that only add load.

Cost: A temporary failure may remain unresolved until a later recovery attempt.

### Retry within limits

When: Another attempt has a reasonable chance of success and the operation is safe to repeat.

Action: Limit attempts and total time; increase delays between attempts and add random variation to avoid synchronized retries.

Gain: Can recover temporary failures without requiring a separate recovery process.

Cost: Adds latency and load; retries can worsen an outage if their limits and delays are poorly chosen.

### Track and reconcile the operation

When: An important remote change must be recovered after a restart or an uncertain response.

Action: Save the operation's identity, determine what completed, and use verified duplicate-prevention guarantees before repeating it.

Gain: Supports recovery without blindly repeating changes that may already have happened.

Cost: Requires durable records and verified rules for duplicate detection, payload matching, and how long those rules remain valid.

## Examples

Example: Retry a timed-out create with the same provider-supported key while its documented guarantee remains valid.

Counterexample: Generating a fresh key on each retry can represent several distinct create intentions rather than one repeated intention.

## Adapt when assumptions change

- The provider adds a documented idempotency guarantee that covers the whole retry interval. Consider bounded automatic retries after validating that contract and the user's latency budget.
- The retention window becomes shorter than possible recovery delays, or key scope changes. Stop relying on the old duplicate-prevention assumption; reconcile first or redesign durable operation tracking.

## Context-adapted validation probes

- Test a timeout before processing and after commitment.
- Test restart, repeated attempts, key expiry or scope boundaries where applicable.
- Confirm the total attempt count and time budget across layers.

- Retries are one of the most common mechanisms that sustain outages; use a retry budget or disable retries under overload. — [Bronson et al., Metastable Failures in Distributed Systems, HotOS 2021](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf)

When: The system has useful behavior and local changes can meet the requirement.

Action: Establish the important existing behavior and change bounded parts while checking that behavior.

Gain: Preserves accumulated behavior and limits migration risk.

Cost: Existing constraints can make each improvement slower or less complete.

### Replace one defined subsystem

When: One subsystem is unsuitable, but its required behavior and integration interface are understood.

Action: Build a replacement behind that interface and migrate gradually with compatibility checks.

Gain: Changes the foundation while limiting how much of the system is exposed at once.

Cost: Both implementations may need support during migration.

### Replace the unsuitable foundation

When: The platform blocks required behavior, or the existing code is disposable and has little behavior to preserve.

Action: Define acceptance checks and plan migration around the actual users, integrations, and data.

Gain: Removes constraints that incremental changes cannot economically resolve.

Cost: Hidden behavior may be lost, and a broad rewrite can postpone usable feedback.

## Examples

Example: Replace a parser behind fixtures drawn from real supported files and a staged rollout path.

Counterexample: Rewriting a stable subsystem merely because its style differs from a new preference does not demonstrate a user benefit.

## Adapt when assumptions change

- The old platform cannot meet a material requirement and its consumers are understood. Consider bounded replacement with explicit behavioral acceptance and migration, rather than extending an unusable foundation indefinitely.
- The behavior is disposable, unshipped, and has no valuable data or consumers. Simplify or replace it without manufacturing legacy preservation work.

## Context-adapted validation probes

- Required old behavior and new requirements are checked explicitly.
- Migration interruption and recovery are covered when persistent state is involved.
- Remaining unknown behavior is disclosed rather than assumed absent.

# P27 — Plan transitions when existing users depend on old behavior

When changing a public contract or stored format, preserve behavior that supported consumers need unless correctness, safety, or a justified retirement requires an explicit break or migration.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Balance consumer continuity with explicit correctness and integrity needs.

Consumer evidence and an explicit support policy distinguish valuable contracts from behavior that should be migrated or retired.

## Context

**Source applicability:** Changing public APIs, identifiers, formats, callback order, command flags, or historical platform workarounds.

**Avoid:** Do not preserve every bug indefinitely, apply compatibility shims speculatively, or interpret missing usage evidence as proof of no consumers.

**Premises:**
- Consumers or persisted data may rely on current behavior.
- The preservation cost and consequences are assessed rather than treated as zero.

## Options and costs

### Preserve relied-on behavior

When: Supported callers depend on the behavior and preserving it has an acceptable cost.

Action: Keep the required behavior and document any quirks that future changes must preserve.

Gain: Avoids disrupting callers or forcing immediate migration.

Cost: Historical constraints and compatibility work continue to accumulate.

### Provide a transition period

When: Callers need time to move, but the old behavior should eventually be retired.

Action: Offer a version or adapter with a stated migration path and retirement conditions.

Gain: Allows the system to improve while callers migrate deliberately.

Cost: Supporting old and new behavior increases testing and support work.

### Make an explicit breaking change

When: Correctness or integrity requires a break, or evidence supports retiring a dependency that no longer has value.

Action: Explain what changes, why the break is justified, and how affected callers or data must migrate.

Gain: Removes harmful behavior or costly constraints that no longer justify preservation.

Cost: Callers can face disruption, migration work, and loss of trust if the change is poorly handled.

## Examples

Example: Maintain an old file reader while new writes use a revised format and users migrate.

Counterexample: Turning on an old compatibility mode for every application can reintroduce behavior that was intentionally changed.

## Adapt when assumptions change

- A historical dependency is removed and the workaround has no remaining supported consumer. Retire it after checking the evidence and the cost of being wrong.
- Preserving behavior now conflicts with an explicit integrity or security requirement. Prioritize that requirement and design a deliberate transition instead of silently retaining the harmful behavior.

## Context-adapted validation probes

- Representative supported consumers still work or can migrate.
- Any deliberate break has an explicit acceptance decision and a tested transition path.

# P28 — Improve performance only where measurements show a real problem

Optimize only when representative measurements show a meaningful resource problem, and keep a change only if it improves the relevant result while preserving required behavior.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Meet the actual resource objective without sacrificing required behavior.

Measurement identifies the limiting resource; comparing designs under the required workload directs effort toward changes that affect the actual objective.

## Context

**Source applicability:** Latency, throughput, memory, contention, or resource use prevents the required outcome or creates a material operating cost.

**Avoid:** Do not remove safety or clarity for an unmeasured hypothetical gain, or assume native/managed language choice determines the result.

**Premises:**
- A performance or resource objective matters to the user or operation.
- The measurement represents the relevant workload and preserves correctness requirements.

## Options and costs

### Keep the clear implementation

When: Representative workloads already meet the required latency, throughput, memory, or cost target.

Action: Retain the readable implementation and a useful measurement baseline.

Gain: Avoids complexity and fragile optimizations with no demonstrated current benefit.

Cost: A different workload may later expose a bottleneck.

### Remove measured expensive work

When: Measurements identify avoidable calls, allocations, repeated computation, or similar waste.

Action: Change that work and measure the effect on the actual end-to-end objective.

Gain: Targets a known cost and lets the result be checked.

Cost: Caching, batching, or reordered work can change freshness, ordering, or failure behavior.

### Change the underlying design

When: Local improvements cannot meet a demonstrated resource requirement.

Action: Reconsider data structures, work ownership, or deployment while preserving required behavior.

Gain: Can remove a bottleneck caused by the structure of the system.

Cost: Migration adds risk and may shift resource use or complexity to another part of the system.

## Examples

Example: Eliminate repeated remote requests when they dominate latency before tuning a small local loop.

Counterexample: A historical whole-system performance result does not establish that rewriting an application in another language will make its user workflow faster.

## Adapt when assumptions change

- Workload scale or access patterns change. Measure the new bottleneck before continuing the old optimization strategy.
- An optimization no longer materially affects the objective. Consider removing its maintenance cost while preserving a useful performance baseline.

## Context-adapted validation probes

- The target outcome improves under a relevant workload.
- Required semantics, failure behavior, and resource bounds remain acceptable.

# P29 — Separate processes or services only when isolation, scaling, or independent releases justify the cost

Give a component its own process or service only when the isolation, scaling, ownership, or deployment benefit justifies the new communication and operating costs.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Choose a deployment boundary that supplies a real lifecycle or isolation benefit.

Keeping code modular locally captures many change benefits; process or service separation is added when independent lifecycle, scaling, or isolation warrants its distinct costs.

## Context

**Source applicability:** Deciding whether a component needs its own process or service.

**Avoid:** Do not infer microservices from Clean Architecture or presume an in-process module supplies process-level failure isolation.

**Premises:**
- The deployment requirement is distinguishable from code organization.
- The team can operate any new failure and ownership boundaries.

## Options and costs

### Keep it in the same process

When: Code separation is sufficient and the components can share a deployment and failure boundary.

Action: Use clear modules within the existing process.

Gain: Keeps calls, shared state, and operations simpler.

Cost: A process failure or resource problem can affect all components in that process.

### Use a separate local worker

When: A local component needs real failure isolation or a separate resource limit.

Action: Move its work into a supervised process and define messages, state ownership, and restart behavior.

Gain: Can contain failures without creating a remote service fleet.

Cost: Adds serialization, process management, coordination, and handling of in-flight work.

### Use a separate service

When: Independent scaling, deployment, or ownership provides a concrete benefit that justifies distribution.

Action: Define the remote contract, data ownership, and behavior for timeouts, partial failure, and recovery.

Gain: Lets the component scale or deploy independently.

Cost: Adds network latency, uncertain outcomes, retries, monitoring, and operating responsibility.

## Examples

Example: Use an isolated local parser process when untrusted parsing needs containment but remote deployment offers no benefit.

Counterexample: Creating a network service solely to make a small class independently testable adds unnecessary failure modes.

## Adapt when assumptions change

- A workload now needs independent scaling or a credible containment boundary. Reassess deployment separation and its state ownership rather than assuming the original shared process remains adequate.
- Independent deployment has no remaining benefit and operations dominate cost. Consider consolidation while retaining useful code contracts.

## Context-adapted validation probes

- The selected boundary provides the actual required lifecycle or isolation benefit.
- Its new operational and failure behaviors are tested at the appropriate boundary.

# P30 — Choose custom code, libraries, or services by required behavior and ongoing cost

Choose custom code, a library, or a service by whether it supplies the required guarantees at a lifecycle cost the team can maintain and justify.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Satisfy the required capability with a maintainable lifecycle commitment.

Comparing the actual required capability, failure behavior, ownership, and update burden avoids choosing by line count or novelty alone.

## Context

**Source applicability:** Selecting a library, framework, external service, or custom helper.

**Avoid:** Do not generalize pragmatic shipping into always build it yourself, or assume package popularity establishes correctness for the use case.

**Premises:**
- The requirement and acceptance boundary are understood.
- The team can maintain the chosen implementation and its relevant guarantees.

## Options and costs

### Build a small local implementation

When: The requirement is bounded and the team can correctly implement and maintain its edge cases.

Action: Implement the required behavior and verify its normal and failure cases.

Gain: Provides direct control with little dependency overhead.

Cost: The team owns every defect, edge case, and future requirement.

### Use a platform feature or library

When: An established component provides the required behavior and guarantees.

Action: Check its fit, failure behavior, integration needs, and update burden before adopting it.

Gain: Reuses existing implementation and specialist knowledge.

Cost: The team still owns integration defects, updates, and dependency constraints.

### Use a managed service

When: A service meets the requirement at a justified total cost compared with building and operating it locally.

Action: Check its guarantees, data handling, recovery behavior, pricing, and exit or replacement path.

Gain: Transfers some implementation and operating work to the provider.

Cost: Creates dependence on the provider's availability, behavior, prices, and migration options.

## Examples

Example: Use a platform primitive for a simple local operation when it satisfies the needed contract.

Counterexample: A short custom implementation is not economical if its apparent simplicity excludes the difficult correctness cases.

## Adapt when assumptions change

- The capability expands into a specialist standard or a broad interoperability problem. Reassess whether maintaining custom code remains cheaper and credible.
- An adopted dependency grows costly while only a tiny stable feature is used. Consider replacing that bounded feature after validating all relied-on behavior.

## Context-adapted validation probes

- The chosen option satisfies representative edge cases and required failure behavior.
- Ownership and the update or replacement path are clear.
