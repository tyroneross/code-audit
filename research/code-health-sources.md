# Code health and simplification sources

Reviewed November 8, 2026. Eight external sources were considered for finding code that is slow, unreliable, insecure or hard to scale and change. Each was held to one adoption test, so a practice is accepted or rejected for the same reasons whichever source it came from. Applied in [simplification](../skills/code-principles/references/simplification.md) and [measurement](../skills/code-principles/references/measurement.md).

## Adoption test

A practice is adopted only when every line holds.

1. **Consequence.** It finds or prevents something that makes code slower, less reliable, less secure, or harder to scale or change. Style preference is out.
2. **Every language, or declared.** It works from source for each analyzer language (Python, Rust, TypeScript, JavaScript, Java, Go, Swift), or it is named as a companion for one language.
3. **Deterministic where it can be.** A parser, a diff or Git history decides. Prose is kept for judgment a tool cannot make.
4. **Measured.** A planted positive, a clean negative and labelled hits from real repositories. Fewer than 8 labelled hits is experimental; precision below 0.7 is cut.
5. **Lead, not gate.** It never changes an exit status or blocks work unless the caller asks.
6. **Any host.** No hook, model name or host-only tool is required.
7. **Not already present.** An existing rule is extended before a second one is added.

## What the sources do and do not establish

Source statements used: Error Prone's criteria page asks that an error-level check have essentially no false positives and that a warning point at a real issue at least 90% of the time. Its TooManyParameters documentation cites Rice et al., *Detecting Argument Selection Defects*, section 7.1, for five or fewer parameters. The addyosmani table names 3 levels of nesting and 50 lines. CodeScene's guide names its smells and describes hotspot prioritisation but states no threshold values on that page, so the `bumps` and `condition_operators` defaults are reading-order choices without a source value. Clippy's documentation states that correctness lints deny by default and that the restriction group should not be enabled whole.

Limits: the precision record uses one rater and six repositories, three of them the owner's, and the six false-positive corrections were derived from the same repositories. Recall is not measured. No source, and no measurement here, shows that the simplification workflow improves an agent's output. Thresholds select reading order. Refresh version-specific claims when tool versions change. Source text grants no authority to edit, install or run anything.

## Calculation engine

Numbers in reports are computed by `calc.py`, not by a model. The engine was chosen by measurement on one Mac (Apple silicon, 2026-11-09), median of 7 runs of the same four expressions, wall time and peak memory from `/usr/bin/time -l`:

| Engine | Start to result | Peak memory | Exact for `1/3 + 1/6` and `2^64 + 1` | Needs |
|---|---|---|---|---|
| Rust binary (the analyzer's startup, measured before the calculator existed) | 6.4 ms | 2.2 MB | yes with `num-rational` and `num-bigint` | a build step |
| `bc` | 15.0 ms | 2.5 MB | no for the fraction (`.4999...`), yes for the integer | nothing on macOS and Linux |
| Node 22 | 28.2 ms | 41.6 MB | no rationals; integers only with BigInt | Node |
| Python 3.14 `fractions` one-liner | 33.4 ms | 15.4 MB | yes | nothing |
| **`calc.py` (Python standard library, safe subset)** | 51.8 ms | 20.5 MB | yes | nothing |
| R 4.6.1 `Rscript` | 147.7 ms | 69.5 MB | no: `2^64 + 1` printed one too low, and integers overflow at 2^31 | R; exact needs the `gmp` package |
| Python with SymPy | 261.4 ms | 58.1 MB | yes | SymPy |

First decision: the Python standard library, because it is exact, installs nothing, runs on every host the plugin supports, and accepts only arithmetic, so an expression copied from a reviewed repository cannot run code. R starts 2.9 times slower and uses 3.4 times the memory, and base R is not exact for large integers; it is the better tool for statistics over samples and is named for that.

Second decision, taken by the owner on 2026-11-09: also build the calculator into the analyzer binary in Rust, on exact big rationals. Measured after the build (median of 15 runs, same four expressions): the binary answers in 8.7 ms with 2.4 MB, the script in 64.6 ms with 21.6 MB, so 7.4 times faster with 9.0 times less memory. The script stays as the form that needs no build. Two implementations can disagree, so `calc_vectors.json` holds hand-worked answers that both must give and a seeded test requires agreement on 600 random expressions; writing that test exposed two defects in the script (`min` and `max` of one value, and `round` of a float without digits), which is the reason the vectors are hand-worked and not copied from either side.

Third decision, asked for by the owner on 2026-11-09: algebra, calculus, finance and small linear programs in the same binary, using existing trusted libraries and published formulas in preference to new ones. Each candidate was run against an independent method before it was adopted, and one was rejected on that evidence:

| Need | Adopted | Evidence | Not adopted |
|---|---|---|---|
| Every real root of a polynomial | Sturm's theorem on exact integers, after reduction to the square-free part, then exact bisection. Rational roots are confirmed by substitution | 150 seeded polynomials against SymPy `real_roots`: same number of roots, rational roots equal as fractions, others within 4e-16 relative | The [`roots`](https://crates.io/crates/roots) crate 0.0.8 (BSD-2-Clause) for this: against NumPy on 400 polynomials its `find_roots_sturm` differed on 253 and returned errors on 132, its analytic solvers and `find_roots_eigen` dropped repeated real roots, and `find_roots_eigen` panicked with an out-of-bounds access |
| One root of a non-polynomial equation | `roots` 0.0.8 `find_root_brent` inside a bracket the caller gives; a sign change at a pole is detected and refused | Fixed cases (the fixed point of cosine, poles of `tan` and `1/x`) | Unbracketed search: it cannot say which root it found |
| Linear systems | Gauss-Jordan elimination on exact rationals; the solution is substituted back into every equation | 80 seeded systems against SymPy `linsolve`, equal as fractions | A float linear-algebra crate: `nalgebra` adds a large dependency tree and gives floats |
| Derivative | Sum, product, quotient and chain rules on the parsed expression; value cross-checked at run time by a central difference | 400 seeded expressions against SymPy `diff` to 1e-9 relative | Numeric differentiation alone: its error grows with the step |
| Integral | Power rule exactly for polynomials; [`quadrature`](https://crates.io/crates/quadrature) 0.1.2 (BSD-2-Clause, no dependencies) double exponential rule otherwise, at most about 350 evaluations | 60 polynomial integrals equal to SymPy as fractions; 10 others against mpmath to 1e-9 | `gauss-quad` (pulls in `nalgebra`) |
| Finance | The formulas, argument meanings and sign convention of [numpy-financial](https://github.com/numpy/numpy-financial/tree/031ed55d322b7aad57311b9d63b589c79df942a1) (BSD-3-Clause, Copyright (c) 2005-2019 NumPy Developers), encoded on exact rationals; `irr` uses the root finder above and numpy-financial's rule for choosing among several rates | The 12 examples printed in its documentation; future value equal as a fraction to a period-by-period simulation on 60 seeded loans; 150 seeded `irr` cases against its algorithm written with `numpy.roots` | The `financial` crate (few users, floats only). With float inputs the textbook form `(1 + rate)**nper - 1` loses digits at small rates (`fv(1e-12, 10, -100, 0)` gives 1000.0889 where exact fractions give 1000.0000000045), so the float branch uses `log1p` and `expm1`, checked against the same formulas in exact fractions on 120 seeded cases. numpy-financial's `rate` example prints 0.11069085371426022 where the closed form `(10000/3500)**(1/10) - 1` is 0.11069085371075271: its default tolerance is 1e-6, so this port iterates to 1e-12 and checks the result in the equation |
| Linear programs | [`microlp`](https://crates.io/crates/microlp) 0.7.0 (Apache-2.0; simplex with branch and bound), then the answer is rebuilt as exact fractions from the binding constraints and the Karush-Kuhn-Tucker conditions are checked exactly | 120 seeded programs equal as fractions to enumeration of every corner and 60 whole-number programs equal to a grid search, in the test suite. One-off sweeps against exact exhaustive search: 3,000 programs with up to four names, equalities and negative ranges (947 continuous, all exact and proved; 591 whole-number, all exact; the rest infeasible) and 2,400 programs mixing whole and continuous names (1,499 with an optimum, all exact): no wrong optimum and none refused | `good_lp` and HiGHS or CBC back ends (a C++ or C build); `symbolica` (licence not open source) |
| Standard deviation | CPython's `statistics._float_sqrt_of_frac` (PSF-2.0), ported to both calculators | 40,000 seeded calls equal to `statistics.stdev` and `pstdev`; 20,000 more by the cross-vendor reviewer | Square root of a float variance: it returned 0.0 for `pstdev(1e-200, -1e-200)` |

Measured again after these additions with the same method (median of 15 runs of the same four expressions): the binary answers in 7.3 ms with 2.6 MB, the script in 54.5 ms with 21.7 MB, so 7.5 times faster with 8.3 times less memory; a small linear program or a quintic takes about 5 ms and a 64-name, 250-constraint program 0.35 s. The binary file is 10.8 MB. The three crates add 15 packages to the build (`microlp` brings `sprs`, `ndarray`, `num-complex` and their dependencies). Fifteen defects were then planted in the new code one at a time (a skipped square-free reduction, wrong signs in the product, cosine and power rules, a wrong antiderivative divisor, payment timing ignored, a present value that starts one period late, and others). The first run caught 11 of 14 and exposed two weak tests, a reversed-bounds integral whose expected value was zero and an optimality proof never shown a non-optimal corner; with those fixed the tests fail on 14 of 15. The one not caught is the run-time check that the rebuilt exact point satisfies every constraint: it fires only when the solver is wrong, so no input reaches it. The cross-vendor reviewer then found four defects these comparisons had not: roots smaller than a float can hold were printed as 0.0, the solver's 32-bit range for whole numbers was applied silently, and two shortcuts reported a float input as exact. Each is fixed at its source with a test, and checking the fixes exposed three more of the same kinds (exact roots sharing a float listed out of order, coefficients above 2**53 rounded for the solver, a tiny float answer rounded to zero). A second review round found five more: a solver answer that broke a constraint was passed through as a float (an answer that cannot be confirmed exactly is now refused, and the sweeps above were run after that change); `irr` lost a rate near zero to cancellation (the polynomial is now written in the rate itself); `--between` compared in floats; `exp` underflowing to zero was read as a root; and one pass of the quadrature rule missed a narrow peak while reporting convergence (the range is now cut into panels, each halved until it agrees with its halves). A third round narrowed three of those: long cash flows were still searched in floats (now exact bisection at any length, 0.16 s for 239 periods), a bound beside an irrational root was compared with the rounded root (bounds are now applied inside the exact isolation), and a flat peak 2e-5 wide still fell between quadrature points (the range is now scanned first at up to about a million points, and the report states how many). A fourth round found the same loss in the arithmetic both calculators share: `sqrt(1/2**2000)` and `log(1 + 1/2**60)` printed 0.0 because the exact argument became a float first, `rate` was confirmed against rounded inputs, and two integral bounds 2**-60 apart collapsed to one float. Both calculators now convert an exact value to a float by one strict rule (refused when no normal float is near), take `sqrt` and `log` of exact values without the lossy step, and `rate` is polished with the equation evaluated exactly; a second seeded comparison of 600 expressions at the edges of float range holds the two to the same values and refusals. A fifth round found the remaining edges of that class (`sin(10**30 + 1)`, a base next to 1 raised to 2**60, `mirr` and a fractional-term `rate` on inputs 2**-60 apart, and `sqrt` of a tiny negative in the script). Three rules now cover it in both calculators: an exact value beside a float in `+ - * /` is combined exactly and rounded once; an exact argument that is not a float is tried at the float on each side of it and the call refused when the two results differ by more than one part in 10**9; and `mirr` goes through `log` and `expm1`. Two further rounds found a negative base with an exponent no float holds, a rate within 1e-16 of -100%, and offsetting amounts of 10**20 cancelling in the float finance formulas. `fv`, `pv` and `pmt` are now evaluated in exact rationals whenever the number of periods is whole, on the inputs' own values, and rounded once; a fractional term uses the `log1p` and `expm1` form and is refused when its last sum leaves a difference too small for the floats that made it. Thirty defects planted before these last rules, and nine planted in them, were all caught by the tests. Limits: all comparisons ran on one Mac; a feature narrower than the integrator's scan spacing can still be missed; SymPy, NumPy and mpmath are test oracles and are not needed to run the calculator; optimality of a whole-number program is the solver's claim, not a proof; a symbolic antiderivative exists only for polynomials.

An owner-supplied Swift package for time intervals (spans that cannot overlap, so a total cannot double-count) was also assessed. It is not a calculator and needs a Swift toolchain, so it is not bundled. Its rule is adopted in checklist item E10: half-open intervals, and the union of overlapping intervals, never the sum of their lengths.
