# P11 — Give each component only the operations it needs

Expose only the coherent capabilities a consumer needs when doing so reduces unwanted dependencies or separates meaningful permissions, without fragmenting operations that belong together.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Limit consumer coupling to the coherent capability it needs.

A cohesive consumer-facing contract limits accidental dependencies and clarifies the actual required capability.

## Context

**Source applicability:** A read-only consumer must depend on write/admin operations, or unrelated interface changes repeatedly affect it.

**Avoid:** Do not split every method into its own interface when callers need one cohesive operation.

**Premises:**
- Consumers have meaningfully different needs.
- Separating those needs reduces coupling without fragmenting one coherent operation.

## Options and costs

### Keep one small interface

When: Callers use the same closely related operations.

Action: Keep those operations in one clearly documented interface.

Gain: Makes the contract easy to find and understand.

Cost: The interface may grow to include operations some callers do not need.

### Expose the needed subset

When: A caller needs only a stable subset, such as reading records without changing them.

Action: Expose that subset while keeping the underlying rule in one place.

Gain: Reduces the number of unrelated changes that affect the caller.

Cost: Additional interface views and mappings must stay consistent.

### Separate capabilities

When: Operations have different permissions, owners, or reasons to change.

Action: Separate the capabilities and enforce the required access rules where the operations run.

Gain: Clarifies which operations a caller can use and reduces unwanted dependencies.

Cost: Adds interfaces and coordination; an interface split alone does not enforce security.

## Examples

Example: A reporting operation receives a query capability rather than a general administrative store.

Counterexample: A transaction's begin, update, and commit operations may need a coherent lifecycle contract rather than unrelated single-method interfaces.

## Adapt when assumptions change

- Consumers converge on the same tightly coupled operations. Consider one coherent contract rather than maintaining artificial fragmentation.
- Permissions or ownership create a real new capability boundary. Separate that capability and validate that callers cannot accidentally acquire broader access.

## Context-adapted validation probes

- A consumer can compile, execute, or be tested using only its required capability.
- An unrelated capability change no longer forces that consumer to change.
