# P06 — Make each value's meaning clear and prevent incorrect use

Give values specific names that communicate their meaning, units, and purpose, and use types and validation checks where needed to prevent values with different meanings from being used interchangeably.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Prevent wrong amounts, wrong record operations, wrong scheduled times, and reliance on unchecked input.

Explicit unit and ID names make a mix-up visible during review; types that enforce the distinction can reject the wrong argument, and entry checks can reject invalid external data.

## Context

**Source applicability:** The same number, string, or date representation can stand for different units, records, or time conventions, or external data has not yet been checked.

**Avoid:** Use names alone when a short local calculation makes the unit unambiguous and extra types would not prevent a plausible mistake. Checking one property, such as a nonempty ID, does not prove which customer it identifies.

**Premises:**
- A concrete mix-up is plausible: for example, a timeout in milliseconds may be passed to a function expecting seconds.
- Names, type checks, validation, and conversions enforce or expose the intended unit, ID kind, time convention, or input rule.

**Audit clarification:** ID and duration checks are examples. Select probes that reveal a consequential value-boundary mistake in the actual contract; local clear names can be sufficient.

## Options and costs

### Use clear names

When: A short local calculation uses one unit or one kind of ID, and a reviewer can inspect all its uses in one place.

Action: Name the value amountInCents, timeoutInSeconds, or customerId so its unit or purpose is visible at each use.

Gain: Makes unit and ID mistakes easier to spot without introducing new types.

Cost: Does not prevent passing amountInCents to a function expecting dollars; the parameter name and value still need to be checked.

### Use distinct types

When: Several functions pass similarly represented values, and a mix-up could change an amount, record, or scheduled time.

Action: Use types such as AmountInCents, CustomerId, OrderId, and UtcTimestamp, with explicit unit and time conversions.

Gain: Can reject passing OrderId to a function that expects CustomerId when those types are actually enforced.

Cost: Adds definitions and conversions; a type alias that still accepts any number or string does not prevent the mix-up.

### Check inputs before use

When: A form or API supplies unchecked data that must satisfy a specific rule, such as a nonnegative amount or a date in UTC.

Action: Parse the input, establish its unit or time convention, check the required range or format, and construct a checked value only after the checks pass.

Gain: Later code can rely on the property that was actually checked, such as amountInCents being nonnegative.

Cost: Requires a defined rejection path; a nonnegative amount can still use the wrong currency, and a well-formed ID can still identify the wrong record.

## Examples

Example: A timeout function expects seconds but receives 5000 milliseconds, so it waits 5000 seconds instead of 5 seconds unless the caller converts the unit.

Counterexample: A loop counter used only inside one short function rarely needs a separate class; an explicit unit in the name may suffice when no other unit enters the calculation.

## Adapt when assumptions change

- An amount or ID that used to come from internal code now arrives through a form or API. Establish its unit from the input contract and validate its format and allowed values before constructing the internal type; a type name is not proof that new input satisfies those rules.
- Text checked for one operation is now inserted into a different output context, such as an HTML page. Use the checks and output encoding required by that context; a length or ID-format check does not make the text safe to render as HTML.

## Context-adapted validation probes

- Try passing OrderId to an operation that expects CustomerId; confirm type checks reject it, or that clear names and checks expose the mismatch.
- Verify that converting 1000 milliseconds produces 1 second, and that storing and reading IDs or dates does not discard their kind, unit, or time convention.
