# P20 — Keep background work supervised until it finishes or stops

When background work can outlive its caller or become obsolete, keep its resources valid until it stops, assign an explicit owner, and prevent stale results from changing current state.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Keep late work from violating resource lifetime or current intent.

Explicit ownership, completion semantics, and request identity keep lifetime and publication decisions aligned with the actual operation.

## Context

**Source applicability:** Using callbacks, asynchronous I/O, background tasks, changing selections, or navigation while work continues.

**Avoid:** Do not add cancellation or generation machinery to a synchronous operation that cannot overlap or outlive its owner.

**Premises:**
- Work can outlive a scope, view, request, or resource owner.
- The implementation distinguishes cancellation requested from work stopped.

## Options and costs

### Finish work within its caller's lifetime

When: Background tasks use resources that the caller will release when it finishes.

Action: Request cancellation where appropriate and wait for the tasks to stop before releasing their resources.

Gain: Prevents late work from accessing resources that no longer exist.

Cost: Waiting for cancellation or completion can delay the caller's response.

### Ignore obsolete results

When: Work can safely continue, but its result no longer belongs to the current view or request.

Action: Retain a valid resource owner and publish the result only if it still matches the current request.

Gain: Prevents an old search or selection result from replacing a newer one.

Cost: Ignoring a result does not stop the task, undo external changes, or release resources.

### Give the job a longer-lived owner

When: The operation must continue after navigation or after the initiating request returns.

Action: Transfer the job to an accountable manager and handle its status separately from view updates.

Gain: Keeps ownership valid for the operation's actual lifetime.

Cost: Completion, failure reporting, cancellation, and any restart persistence need explicit handling.

## Examples

Example: A preview result is published only if it still belongs to the active selection.

Counterexample: Setting a canceled flag does not establish that a task stopped using the resource the caller is about to release.

## Adapt when assumptions change

- Work must now survive navigation. Move its ownership beyond the view and separate durable completion from view updates.
- The implementation becomes synchronous and cannot produce late results. Remove redundant stale-result machinery while retaining required resource guarantees.

## Context-adapted validation probes

- Exercise owner disappearance, rapid superseding requests, late success, and late failure.
- Confirm resources are released only after their actual users finish or ownership is safely transferred.
