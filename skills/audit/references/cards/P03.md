# P03 — Use safe defaults and ask users when their judgment is needed

When a workflow requires a choice, use a safe default for implementation details and ask the user when their preferences, judgment, or authority are necessary.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Let users complete tasks and make meaningful informed choices.

Task-based defaults and observed usability reduce unnecessary decisions and reveal whether users can complete the real workflow.

## Context

**Source applicability:** Users face technical options, confusing errors, invisible state, or a workflow whose success cannot be inferred from code alone.

**Avoid:** The choice expresses meaningful intent, has consequences only the user can judge, or requires the user's authority.

**Premises:**
- The system has enough information to choose safely, or a useful default can be reversed.
- The decision is an implementation detail rather than a material user preference or authorization.

## Options and costs

### Choose a safe default

When: The system can determine a safe implementation choice and the user can easily reverse it.

Action: Apply the default and provide a clear way to change or undo it.

Gain: Lets the user finish the task with fewer interruptions.

Cost: A wrong default can hide a consequence the user would have chosen differently.

### Offer optional controls

When: Most users can use the default, but some need to adjust the behavior.

Action: Provide a useful default and make additional controls available when needed.

Gain: Keeps the common task simple while allowing informed adjustments.

Cost: Users may not discover a control they need if it is hidden too deeply.

### Ask for a decision

When: The choice depends on the user's preferences, acceptable loss or cost, or authority.

Action: Explain the actual consequences and ask for the decision needed to proceed.

Gain: Preserves the user's control over outcomes the system cannot choose for them.

Cost: Adds a step; asking about implementation trivia creates unnecessary work.

## Examples

Example: An importer detects supported encodings automatically when detection is reliable and the user can preview the result.

Counterexample: The software must not infer that a user wants to discard conflicting records merely to avoid a dialog.

## Adapt when assumptions change

- A formerly internal choice now determines user-visible cost or data loss. Make that consequence explicit and obtain the required choice instead of silently applying the old default.
- The system can now determine a formerly technical choice reliably. Remove the unnecessary prompt while retaining a useful recovery or override path.

## Context-adapted validation probes

- A representative user can complete the task and understand the resulting state.
- The product does not silently choose a material preference or conceal an unresolved failure.
