# P16 — Handle failures where enough context exists to respond safely

Handle a failure at the component that can take a useful, safe next action; otherwise preserve context and pass it to that component.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Return truthful outcomes and preserve useful failure context.

A deliberate error owner combines the failure with enough application context to recover, translate, explain, or contain it.

## Context

**Source applicability:** Choosing catch locations, mapping dependency errors, or defining a user-facing failure boundary.

**Avoid:** Do not catch solely to silence an error, report success, or repeat the same logging at each layer.

**Premises:**
- The handler has an actual next action and knows the affected state.
- Translation preserves the stable meaning needed by callers.

## Options and costs

### Recover in this component

When: A fallback can preserve the behavior promised to the caller.

Action: Apply the fallback and report any reduced capability that matters to the caller.

Gain: Resolves the failure close to its cause and simplifies callers.

Cost: A fallback can appear successful while silently changing the meaning of the result.

### Pass the failure to its owner

When: The caller has the context or authority to choose recovery, reporting, or a user decision.

Action: Pass the failure with the operation, relevant state, and cause needed to make that decision.

Gain: Places the response where the necessary information and responsibility exist.

Cost: Useful local details can be lost if they are not included during propagation.

### Stop at a safe boundary

When: Continuing would use state whose validity is unknown.

Action: Stop the affected component and report a failed or uncertain outcome accurately.

Gain: Protects state integrity instead of reporting a false success.

Cost: Interrupts work and requires a recovery policy appropriate to that component.

## Examples

Example: A query boundary distinguishes no matching records from a failed database query.

Counterexample: Returning an empty list after every database exception misrepresents unavailable data as a confirmed empty result.

## Adapt when assumptions change

- A lower component gains a reliable local fallback that preserves the contract. Move that recovery downward while preserving visibility of degraded behavior when relevant.
- A fallback now changes meaning or loses required data. Stop treating it as recovery; expose rejection, partial completion, or a decision for the caller.

## Context-adapted validation probes

- A material failure reaches an owner who can act.
- The caller receives a truthful outcome and diagnostics preserve the original cause.
- Earlier effects remain accounted for after the handler returns.

## Research update (2026-10-14)

- 35% of catastrophic failures matched three trivial handler patterns (empty or log-only, over-broad abort, TODO); 58% would have been caught by testing the error-handling code. Test every handler. — [Yuan et al., OSDI 2014](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf)
