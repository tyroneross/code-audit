# P18 — Define what happens when an operation succeeds only in part

If an operation can fail after changing visible or persistent state, define which effects commit together and how incomplete effects will be reported, rolled back, or reconciled.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Keep observable state within the operation's permitted guarantees.

Private preparation and a deliberate commitment boundary control which states become observable; reconciliation accounts for effects that cannot commit atomically.

## Context

**Source applicability:** An operation has several effects, publishes shared state, or can fail after making a persistent change.

**Avoid:** Do not add staging around a single operation already covered by a sufficient atomic guarantee, or assume resource cleanup reverses persistent effects.

**Premises:**
- The required invariant and observation boundary are identified.
- Atomicity, rollback, and compensation are claimed only for effects they actually cover.

## Options and costs

### Use one all-or-nothing operation

When: One transaction or atomic primitive covers all changes that must succeed or fail together.

Action: Use that guarantee and check what happens when the operation fails.

Gain: Provides all-or-nothing changes within the guarantee's actual scope.

Cost: An email, remote request, or other effect outside that scope is still separate.

### Prepare before publishing

When: Work can be prepared privately and made visible at one defined commit point.

Action: Complete preparation first, then publish the result through that commit point.

Gain: Prevents readers from seeing incomplete preparation.

Cost: Preparation can require extra storage, memory, time, or temporary copies.

### Track partial completion

When: Required effects cannot all be included in one sufficient transaction.

Action: Record which effects completed, report partial status, and reconcile or compensate the remaining effects.

Gain: Provides accurate status and a deliberate path toward a consistent outcome.

Cost: Recovery is more complex, and compensation may not fully reverse an external effect.

## Examples

Example: Publish a document only after its required source reference and content are valid.

Counterexample: Closing a network connection after an exception does not undo a record already created on the remote server.

## Adapt when assumptions change

- A new storage transaction now covers every required effect. Use it and simplify redundant application staging after checking the actual transaction boundary.
- A new remote effect lies outside the local transaction. Add an explicit gap and reconciliation policy; the earlier atomicity assumption is no longer sufficient.

## Context-adapted validation probes

- Inject or simulate a material failure between consequential steps.
- Check that readers see only permitted states.
- Check interruption and restart behavior when persistent effects exist.
