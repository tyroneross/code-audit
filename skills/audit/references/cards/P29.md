# P29 — Separate processes or services only when isolation, scaling, or independent releases justify the cost

Give a component its own process or service only when the isolation, scaling, ownership, or deployment benefit justifies the new communication and operating costs.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Choose a deployment boundary that supplies a real lifecycle or isolation benefit.

Keeping code modular locally captures many change benefits; process or service separation is added when independent lifecycle, scaling, or isolation warrants its distinct costs.

## Context

**Source applicability:** Deciding whether a component needs its own process or service.

**Avoid:** Do not infer microservices from Clean Architecture or presume an in-process module supplies process-level failure isolation.

**Premises:**
- The deployment requirement is distinguishable from code organization.
- The team can operate any new failure and ownership boundaries.

## Options and costs

### Keep it in the same process

When: Code separation is sufficient and the components can share a deployment and failure boundary.

Action: Use clear modules within the existing process.

Gain: Keeps calls, shared state, and operations simpler.

Cost: A process failure or resource problem can affect all components in that process.

### Use a separate local worker

When: A local component needs real failure isolation or a separate resource limit.

Action: Move its work into a supervised process and define messages, state ownership, and restart behavior.

Gain: Can contain failures without creating a remote service fleet.

Cost: Adds serialization, process management, coordination, and handling of in-flight work.

### Use a separate service

When: Independent scaling, deployment, or ownership provides a concrete benefit that justifies distribution.

Action: Define the remote contract, data ownership, and behavior for timeouts, partial failure, and recovery.

Gain: Lets the component scale or deploy independently.

Cost: Adds network latency, uncertain outcomes, retries, monitoring, and operating responsibility.

## Examples

Example: Use an isolated local parser process when untrusted parsing needs containment but remote deployment offers no benefit.

Counterexample: Creating a network service solely to make a small class independently testable adds unnecessary failure modes.

## Adapt when assumptions change

- A workload now needs independent scaling or a credible containment boundary. Reassess deployment separation and its state ownership rather than assuming the original shared process remains adequate.
- Independent deployment has no remaining benefit and operations dominate cost. Consider consolidation while retaining useful code contracts.

## Context-adapted validation probes

- The selected boundary provides the actual required lifecycle or isolation benefit.
- Its new operational and failure behaviors are tested at the appropriate boundary.
