# P10 — Preserve behavior that callers rely on when replacing code

Use an implementation as a substitute only if it accepts all permitted inputs and preserves the behavior and guarantees that existing callers rely on.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Keep intended substitutes safe for existing callers.

Contract checks detect substitutions that would invalidate assumptions already embedded in callers.

## Context

**Source applicability:** Introducing a new adapter, subtype, fake, backend, or framework implementation behind an existing interface.

**Avoid:** Do not claim interchangeability when one implementation requires stricter inputs or supplies weaker required results.

**Premises:**
- Callers are intended to use the implementations interchangeably.
- Their required behavior can be described independently of a particular implementation.

## Options and costs

### Substitute directly

When: The replacement accepts permitted inputs and preserves every guarantee the existing callers need.

Action: Run the same behavioral contract checks against the original and replacement.

Gain: Changes the implementation with few caller changes.

Cost: Matching method names and types can hide differences in errors, ordering, or state changes.

### Adapt the missing behavior

When: An adapter can reliably provide a required guarantee that the replacement lacks.

Action: Implement the missing guarantee explicitly and test it under relevant failures.

Gain: Preserves caller expectations while using a different underlying implementation.

Cost: The adapter may add state, latency, resource use, and new failure modes.

### Change the caller contract

When: The required behavior cannot be preserved at an acceptable cost.

Action: Expose the actual capabilities and migrate affected callers and tests deliberately.

Gain: Makes the new limitations visible instead of silently breaking expectations.

Cost: Callers must change, and the migration can disrupt existing uses.

## Examples

Example: A fake store must reproduce conflict behavior if application recovery depends on conflicts.

Counterexample: A memory-only fake that never rejects writes is insufficient evidence for a persistent adapter's failure behavior.

## Adapt when assumptions change

- The new backend cannot preserve required ordering or consistency. Supply that guarantee explicitly or change the application contract and callers; do not rely on identical method names.
- The application no longer relies on a historical guarantee. Relax the contract deliberately and update tests and consumers accordingly.

## Context-adapted validation probes

- Shared behavioral checks pass for every intended substitute.
- Representative real dependency behavior agrees with the contract, including failures.
