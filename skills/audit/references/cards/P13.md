# P13 — Split code only when the whole operation becomes easier to understand

Extract a function or module only when its name and interface reduce the total context needed to understand, use, and change the operation.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Reduce the complete operation's understanding and maintenance cost.

A good boundary hides meaningful complexity behind a simpler contract and keeps the operation's invariant coherent.

## Context

**Source applicability:** Independent responsibilities or a reusable difficult operation can be understood behind a clear boundary.

**Avoid:** Do not use a universal line limit or extract code whose interface is as complicated as its body.

**Premises:**
- The proposed extraction has a comprehensible contract.
- It reduces the total context needed for the affected tasks.

## Options and costs

### Keep the operation together

When: The operation is readable in one place and its steps share substantial context or state.

Action: Use one clearly structured function rather than splitting each step into a separate call.

Gain: Lets a reader follow the complete operation without jumping between files.

Cost: The function can become difficult to understand if unrelated work is added.

### Extract a focused helper

When: A named step has a simple input and output and requires little surrounding context.

Action: Extract that step with a name and interface that explain what the caller can rely on.

Gain: Removes distracting detail from the caller.

Cost: Adds navigation and parameter passing; a poor helper merely moves the same complexity.

### Create a module that hides complexity

When: A substantial subsystem can offer a small interface that hides difficult internal work.

Action: Keep the subsystem's rules and state together and expose only what callers need.

Gain: Lets callers use the capability without understanding most of its implementation.

Cost: A poor interface leaks internal details or creates layers that only forward calls.

## Examples

Example: An importer hides decoding and validation behind a result that communicates usable content or an actionable rejection.

Counterexample: Five one-line wrappers with identical parameters may add more navigation than understanding.

## Adapt when assumptions change

- The extracted helpers repeatedly require the same large shared state. Reconsider their boundary or combine them around one owner.
- One embedded operation becomes independently complex or reusable. Extract it when a simple contract now removes substantial detail.

## Context-adapted validation probes

- A reviewer can explain the operation with fewer unrelated concepts.
- Representative changes avoid duplicated logic or extensive cross-file edits.

## Research update (2026-10-14)

- After controlling for class size, design metrics no longer predicted faults: total code size dominates. Splitting without shrinking buys no defect reduction. — [El Emam et al., The Confounding Effect of Class Size, IEEE TSE 2001 (read via summary)](https://neverworkintheory.org/2011/07/07/the-confounding-effect-of-class-size-on-the-validity-of-object-oriented-metrics.html)
- Martin and Ousterhout debate method length, comments and TDD directly; Martin recommends very short functions, Ousterhout says benefit falls as methods shrink. — [Ousterhout & Martin, aposd-vs-clean-code (2024–2025)](https://github.com/johnousterhout/aposd-vs-clean-code)
