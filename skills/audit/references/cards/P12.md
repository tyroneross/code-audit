# P12 — Separate business rules from databases, frameworks, and services

Separate durable business rules from frameworks and external services when that lets the rules change or be tested independently at a justified maintenance cost.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Keep durable policy economical to change and verify.

Policy defines the capabilities it needs; boundary adapters translate external representations and implement those capabilities.

## Context

**Source applicability:** A core rule cannot run without a web server, UI, or database setup, or mechanism changes repeatedly force policy edits.

**Avoid:** Do not reproduce a layered architecture diagram in a tiny program that has no independent policy or variation.

**Premises:**
- There is substantive policy with an expected life beyond the current mechanism.
- The boundary can reduce coupling without hiding semantics the policy requires.

## Options and costs

### Use the framework directly

When: The component is a simple or short-lived adapter with no independent business rules.

Action: Use the framework directly where it keeps the implementation clear.

Gain: Avoids layers and duplicate data models with no current benefit.

Cost: Business rules added later may become difficult to separate from the framework.

### Extract the business rules

When: Rules can be expressed using explicit inputs and outputs, without performing I/O inside the rule.

Action: Put those decisions in small functions and handle storage, network calls, or UI effects outside them.

Gain: Makes the rules easier to reason about and test in isolation.

Cost: Data conversion and integration code still need maintenance and testing.

### Let rules own the interfaces

When: Long-lived rules serve several interfaces or depend on integrations that change frequently.

Action: Define the interfaces the rules require and make database, network, or UI adapters implement them.

Gain: Lets rules evolve with less dependence on a particular framework or provider.

Cost: Adds interface definitions, adapters, and data mappings that must be maintained.

## Examples

Example: Pricing rules run independently of HTTP request objects and database row classes.

Counterexample: A small command that copies a file does not automatically need entities, repositories, use-case classes, and presenters.

## Adapt when assumptions change

- The program is a short-lived adapter with no independent business policy. Use the framework directly where clearer; avoid empty layers.
- Rules gain a second delivery channel or substantial independent evolution. Extract the shared policy around its observed requirements.

## Context-adapted validation probes

- Important policy can be checked with controlled inputs without launching unnecessary mechanisms.
- The real adapter still satisfies the policy's required guarantees.
