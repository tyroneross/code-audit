# P22 — Choose when to write tests and when to explore first

For lasting or consequential behavior, write meaningful tests before or alongside implementation when expected outcomes are known, and explore first when they are not.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Establish meaningful feedback for durable behavior without low-value ceremony.

Writing behavioral examples before or alongside logic clarifies outcomes and supplies regression feedback when the behavior is understood.

## Context

**Source applicability:** Developing rules, transformations, state transitions, or a regression whose expected behavior can be stated concretely.

**Avoid:** Do not require accessor tests, implementation-mirroring assertions, or a fixed test-first sequence for disposable visual exploration.

**Premises:**
- There is meaningful behavior with a useful expected-result oracle.
- The behavior is durable or failure is consequential enough to justify automated feedback.

## Options and costs

### Explore or inspect first

When: The intended behavior is unknown, appearance needs inspection, or the edit is small and easily reversed.

Action: Prototype the unknown behavior or inspect the actual rendered result.

Gain: Gets useful feedback before writing tests around an assumed answer.

Cost: Behavior that later becomes relied upon still needs suitable regression checks.

### Write the behavioral test first

When: The expected outcome is known and an example can clarify a rule that will be maintained.

Action: Write a failing example of the required behavior, then implement that behavior.

Gain: Clarifies the result before implementation and detects later regressions.

Cost: A test of the wrong requirement or internal implementation can constrain later improvements.

### Explore, then add regression checks

When: An experiment has established behavior that the product will now maintain.

Action: Add tests of that observed, intended behavior before more code or users depend on it.

Gain: Preserves what the experiment established without pretending it was known in advance.

Cost: Code written for exploration may need changes before its behavior can be tested reliably.

## Examples

Example: Write conflict-resolution examples before implementing a durable merge rule.

Counterexample: A test asserting that a trivial accessor returns the exact field it immediately returns may add no useful assurance.

## Adapt when assumptions change

- Exploration has produced an agreed durable behavior. Add meaningful regression checks before further dependence or broad modification.
- A test mostly asserts internal plumbing and produces no useful defect signal. Replace it with a behavioral or boundary check, or remove the redundant test.

## Context-adapted validation probes

- Checks would detect a plausible consequential defect or regression.
- Refactoring internal structure does not require changing tests that describe unchanged behavior.

## Research update (2026-10-14)

- Quality and productivity tracked small, uniform test-and-code cycles; writing the test first versus last had no important effect. TDD research overall is inconclusive. Emphasize small steady steps over test-first order. — [Fucci et al., A Dissection of the TDD Process, IEEE TSE 2017; Ghafari et al., ESEM 2020](https://arxiv.org/abs/1611.05994)
