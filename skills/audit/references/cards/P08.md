# P08 — Keep code together when it changes for the same reason

Separate code when its parts change for different reasons or owners, and keep it together when splitting would scatter one coherent rule.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Localize changes without scattering one coherent rule.

Cohesion keeps knowledge that changes together in one place and separates genuinely different change drivers.

## Context

**Source applicability:** A module mixes independently changing business rules, presentation, persistence, or external protocols.

**Avoid:** Do not equate one responsibility with one method, one statement, or a fixed file size.

**Premises:**
- The proposed responsibilities have different owners, rules, or change patterns.
- The split reduces coupling more than it adds navigation and coordination.

## Options and costs

### Keep one rule together

When: The operations change together and rely on the same rule and state.

Action: Keep the rule and its required state under one module or component.

Gain: Avoids spreading one change across several files and interfaces.

Cost: Unrelated responsibilities can accumulate if later changes are not reviewed.

### Separate an independent part

When: A mechanism, such as storage or formatting, changes independently of the surrounding business rule.

Action: Move that part behind a small interface while leaving the shared rule in one place.

Gain: Lets the independent part change with fewer edits to the business rule.

Cost: Adds an interface, more navigation, and mapping between the parts.

### Assign separate owners

When: Responsibilities have different owners, release needs, or patterns of change.

Action: Give each responsibility a clear module or component and define how they interact.

Gain: Supports independent changes and makes responsibility for defects clearer.

Cost: A split across code that must change together adds coordination without real independence.

## Examples

Example: Separate tax-policy calculation from a vendor-specific persistence mapping when they evolve independently.

Counterexample: Splitting each validation predicate into a separate class can scatter one coherent validation rule.

## Adapt when assumptions change

- Two responsibilities repeatedly change for the same reason and require intimate shared state. Consider combining them or moving the shared rule into one owner.
- A formerly unified policy gains independent owners and release requirements. Reconsider the boundary using those actual change drivers.

## Context-adapted validation probes

- A representative policy change stays within a coherent area.
- The complete operation remains understandable and does not require duplicated knowledge across modules.
