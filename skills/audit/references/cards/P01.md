# P01 — Define what the software should do before coding

Before coding, clarify expected behavior with concrete examples whenever different interpretations could change the result.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Implement the intended behavior with avoidable ambiguity resolved.

Concrete examples expose incompatible interpretations while changing the design is still cheap.

## Context

**Source applicability:** Inputs, acceptance criteria, partial completion, or the caller's next action admit consequential alternative interpretations.

**Avoid:** The existing contract already answers the question, or the change is a small reversible adjustment whose outcome is obvious.

**Premises:**
- A material behavior choice remains unresolved.
- Clarifying it costs less than likely rework or a wrong result.

## Options and costs

### Reuse or prototype

When: Existing behavior is already defined, or the user need is still being discovered.

Action: Reuse the existing examples when behavior is known; prototype the task when the need is unknown.

Gain: Gets feedback without documenting assumptions as settled requirements.

Cost: Hidden assumptions may survive, and prototype behavior may need revision.

### Write concrete examples

When: Different interpretations of success, failure, or partial completion would produce different code.

Action: Write examples showing accepted inputs, rejected inputs, visible changes, and rules that must remain true.

Gain: Exposes disagreements before implementation makes them expensive to fix.

Cost: Examples must be updated when the intended behavior changes.

### Define an explicit contract

When: Several callers or costly side effects depend on exactly the same behavior.

Action: Specify normal outcomes, important edge cases, permitted effects, and checks at the public boundary.

Gain: Gives implementations and callers a shared definition of correct behavior.

Cost: Detailed specifications take time and can lock in an untested requirement.

## Examples

Example: A batch import must decide whether one invalid item rejects the batch or produces a partial result.

Counterexample: Correcting a misspelled button label does not justify inventing an application architecture brief.

## Adapt when assumptions change

- The main unknown is what users need, rather than how to implement an agreed behavior. Prototype and observe the task before freezing a detailed specification; preserve a clear experimental question.
- The behavior is now established and the change is purely presentational. Reuse the contract and perform the relevant rendered check; omit a new design document.

## Context-adapted validation probes

- A success example and a material failure example have unambiguous expected outcomes.
- The delivered behavior satisfies those outcomes at the relevant boundary.
