# P27 — Plan transitions when existing users depend on old behavior

When changing a public contract or stored format, preserve behavior that supported consumers need unless correctness, safety, or a justified retirement requires an explicit break or migration.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Balance consumer continuity with explicit correctness and integrity needs.

Consumer evidence and an explicit support policy distinguish valuable contracts from behavior that should be migrated or retired.

## Context

**Source applicability:** Changing public APIs, identifiers, formats, callback order, command flags, or historical platform workarounds.

**Avoid:** Do not preserve every bug indefinitely, apply compatibility shims speculatively, or interpret missing usage evidence as proof of no consumers.

**Premises:**
- Consumers or persisted data may rely on current behavior.
- The preservation cost and consequences are assessed rather than treated as zero.

## Options and costs

### Preserve relied-on behavior

When: Supported callers depend on the behavior and preserving it has an acceptable cost.

Action: Keep the required behavior and document any quirks that future changes must preserve.

Gain: Avoids disrupting callers or forcing immediate migration.

Cost: Historical constraints and compatibility work continue to accumulate.

### Provide a transition period

When: Callers need time to move, but the old behavior should eventually be retired.

Action: Offer a version or adapter with a stated migration path and retirement conditions.

Gain: Allows the system to improve while callers migrate deliberately.

Cost: Supporting old and new behavior increases testing and support work.

### Make an explicit breaking change

When: Correctness or integrity requires a break, or evidence supports retiring a dependency that no longer has value.

Action: Explain what changes, why the break is justified, and how affected callers or data must migrate.

Gain: Removes harmful behavior or costly constraints that no longer justify preservation.

Cost: Callers can face disruption, migration work, and loss of trust if the change is poorly handled.

## Examples

Example: Maintain an old file reader while new writes use a revised format and users migrate.

Counterexample: Turning on an old compatibility mode for every application can reintroduce behavior that was intentionally changed.

## Adapt when assumptions change

- A historical dependency is removed and the workaround has no remaining supported consumer. Retire it after checking the evidence and the cost of being wrong.
- Preserving behavior now conflicts with an explicit integrity or security requirement. Prioritize that requirement and design a deliberate transition instead of silently retaining the harmful behavior.

## Context-adapted validation probes

- Representative supported consumers still work or can migrate.
- Any deliberate break has an explicit acceptance decision and a tested transition path.

## Research update (2026-10-14)

- Advisory deprecation rarely produces migration; compulsory deprecation needs a deadline, enforcement and an owning team. Code is a liability, not an asset. — [Software Engineering at Google, ch. 15 Deprecation](https://abseil.io/resources/swe-book/html/ch15.html)
- Missing usage evidence is not proof of no consumers. — [Hyrum's Law](https://www.hyrumslaw.com/)
