# P14 — Classify failures by the safe next action

When an operation fails, classify the failure by what the responsible component can safely do next, based on the actual operation and affected state.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Give each meaningful failure an appropriate next action and owner.

Separating cause from recoverability and responsibility identifies the component capable of restoring a valid state or selecting an alternative.

## Context

**Source applicability:** Designing an API's failure contract or deciding whether to reject, recover, retry, cancel, reconcile, or contain.

**Avoid:** Do not infer recoverability from outside our control, transient, exception, or panic alone.

**Premises:**
- The affected state and operation contract are known enough to assess recovery.
- The classification is specific to this boundary, rather than a universal label attached to the error type.

## Options and costs

### Return a small set of outcomes

When: Several different causes require the same response from the caller.

Action: Return stable application outcomes and retain detailed causes for diagnosis.

Gain: Keeps caller decisions simple and less dependent on provider-specific errors.

Cost: Combining failures too broadly can remove information needed to recover.

### Distinguish actionable failures

When: Different failures require different responses, such as correcting input, retrying, or checking an uncertain result.

Action: Define failure categories around those actual next actions.

Gain: Lets the caller choose a response that fits the failure.

Cost: Too many categories make callers depend on details that may change.

### Contain an internal defect

When: A required state rule has failed and safe continuation has not been established.

Action: Preserve diagnostic information and stop the component needed to contain the affected state.

Gain: Prevents continued use of potentially corrupted state.

Cost: Work becomes unavailable at that boundary; preserving other work depends on actual isolation.

## Examples

Example: An unsupported customer file is an actionable rejection; an impossible internal parser state may be a defect.

Counterexample: A network timeout outside the programmer's control is not automatically safe to retry.

## Adapt when assumptions change

- A failure previously impossible in valid input becomes an expected user case. Provide a supported rejection or recovery contract rather than treating the user case as an internal bug.
- Recovery now requires state owned by a different component. Move the decision to that owner and preserve the information it needs.

## Context-adapted validation probes

- Each material failure has a defined next action and truthful resulting state.
- No external write is reclassified as known failure solely because its response timed out.
