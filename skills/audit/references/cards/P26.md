# P26 — Choose gradual improvement or replacement without losing required behavior

Improve existing code incrementally when that preserves useful behavior at lower risk, and replace it when required benefits justify the migration and verification costs.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Improve unsuitable code while preserving valuable behavior and data.

Behavioral evidence and staged migration preserve useful knowledge while allowing an unsuitable mechanism to be replaced deliberately.

## Context

**Source applicability:** Changing a legacy subsystem, save format, protocol, or central architecture.

**Avoid:** Do not interpret rewrite warnings as a permanent ban on replacement, or unreadable code as sufficient proof that replacement is cheaper.

**Premises:**
- Some existing behavior or data has value that must survive.
- The proposed route is evaluated against actual requirements and migration cost.

## Options and costs

### Improve the existing code in stages

When: The system has useful behavior and local changes can meet the requirement.

Action: Establish the important existing behavior and change bounded parts while checking that behavior.

Gain: Preserves accumulated behavior and limits migration risk.

Cost: Existing constraints can make each improvement slower or less complete.

### Replace one defined subsystem

When: One subsystem is unsuitable, but its required behavior and integration interface are understood.

Action: Build a replacement behind that interface and migrate gradually with compatibility checks.

Gain: Changes the foundation while limiting how much of the system is exposed at once.

Cost: Both implementations may need support during migration.

### Replace the unsuitable foundation

When: The platform blocks required behavior, or the existing code is disposable and has little behavior to preserve.

Action: Define acceptance checks and plan migration around the actual users, integrations, and data.

Gain: Removes constraints that incremental changes cannot economically resolve.

Cost: Hidden behavior may be lost, and a broad rewrite can postpone usable feedback.

## Examples

Example: Replace a parser behind fixtures drawn from real supported files and a staged rollout path.

Counterexample: Rewriting a stable subsystem merely because its style differs from a new preference does not demonstrate a user benefit.

## Adapt when assumptions change

- The old platform cannot meet a material requirement and its consumers are understood. Consider bounded replacement with explicit behavioral acceptance and migration, rather than extending an unusable foundation indefinitely.
- The behavior is disposable, unshipped, and has no valuable data or consumers. Simplify or replace it without manufacturing legacy preservation work.

## Context-adapted validation probes

- Required old behavior and new requirements are checked explicitly.
- Migration interruption and recovery are covered when persistent state is involved.
- Remaining unknown behavior is disclosed rather than assumed absent.

## Research update (2026-10-14)

- Like-for-like rewrites usually fail; replace gradually behind seams, smallest parts first. — [Fowler, Strangler Fig Application (updated 2024)](https://martinfowler.com/bliki/StranglerFigApplication.html)
