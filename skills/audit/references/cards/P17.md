# P17 — Stop work that could use corrupted data or invalid resources

When a failure makes state unsafe to use, stop the operation, worker, or process needed to contain the damage, and continue unrelated work only if its state remains trustworthy.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Prevent use of untrustworthy state while preserving valid unrelated work.

Stopping the affected owner prevents further use of its invalid state while a trustworthy surrounding owner preserves or reconciles other work.

## Context

**Source applicability:** An internal defect, resource failure, or lifetime violation prevents a component from honoring its contract.

**Avoid:** Do not crash for ordinary invalid user input or assume a thread or coroutine isolates shared memory and external effects.

**Premises:**
- The failure makes continued use of affected state unsafe or defeats a required guarantee.
- The proposed boundary's owned and shared state are understood.
- Restart and outstanding external effects have a defined policy.

## Options and costs

### Reject only this operation

When: The failure leaves both this operation's state and shared state valid.

Action: Reject the operation or roll back its changes, then allow unrelated work to continue.

Gain: Limits disruption while returning an accurate failure.

Cost: A wrong assumption about shared state can let damage spread to later operations.

### Stop an isolated worker

When: The worker's isolation actually contains its damaged state and effects.

Action: Stop or restart the worker under a supervisor and account for outstanding effects.

Gain: Contains the failure while other isolated workers continue.

Cost: Isolation, worker startup, and coordination require resources and operating logic.

### Stop the process holding shared state

When: The failure may have corrupted state shared within the process or a broader owning component.

Action: Stop that owner and recover from state that is known to be valid.

Gain: Prevents later work from using possibly corrupted shared state.

Cost: Interrupts more work and may require replay, reconciliation, or manual recovery.

## Examples

Example: A disposable parser process can stop on an internal invariant failure while its supervisor marks the input for investigation.

Counterexample: A malformed customer filename is not sufficient reason to terminate a healthy multi-user service.

## Adapt when assumptions change

- An isolated worker is merged into a shared application process. Reassess the failure boundary; do not inherit the old whole-process abandonment policy automatically.
- The failure may already have corrupted shared state. Broaden containment or stop the shared owner rather than catching and continuing as if isolation still held.

## Context-adapted validation probes

- Unrelated state remains valid under the intended containment design.
- A restart does not blindly duplicate outstanding effects.
- The actual runtime's termination and cleanup behavior matches the design.

## Research update (2026-10-14)

- Let it crash works because processes share nothing and a supervisor recovers; without both, crashing is not a strategy. — [Armstrong, Making reliable distributed systems in the presence of software errors (2003), §4.3–4.4](https://erlang.org/download/armstrong_thesis_2003.pdf)
