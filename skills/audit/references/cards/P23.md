# P23 — Verify the actual outcome before claiming the change works

Before claiming a change works, run a check that observes the behavior at the claimed boundary, whether that is logic, integration, rendered UI, installation, or deployment.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Support each completion claim with evidence at its actual boundary.

A deliberate claim-to-evidence match exposes modeled assumptions and verifies the actual changed operation where necessary.

## Context

**Source applicability:** Selecting validation for logic, adapters, integration, visible UI, packaging, installation, or deployment.

**Avoid:** Do not run every available check for every small change, or claim runtime success from source inspection or a build alone.

**Premises:**
- The claimed completion boundary is explicit.
- The chosen check observes the behavior relevant to that claim.

## Options and costs

### Check the isolated rule

When: The claim concerns a deterministic calculation, transformation, or state rule.

Action: Check representative inputs, expected outputs, and the edge cases that could change the result.

Gain: Provides fast feedback about that rule's correctness.

Cost: Does not prove the rule is connected correctly to real dependencies or the delivered product.

### Exercise the real integration or UI

When: The change depends on a provider, configuration, adapter, or visible interface.

Action: Run the operation through the relevant real connection or inspect and exercise the rendered UI.

Gain: Checks assumptions that an isolated unit test cannot observe.

Cost: Requires more setup and may introduce slower or less predictable checks.

### Verify the delivered state

When: The claim is that a change is installed, deployed, migrated, or working for users.

Action: Verify that specific delivered version or state and exercise representative behavior there.

Gain: Supports the actual delivery claim instead of inferring it from a successful build.

Cost: Requires access to the delivered environment and checks appropriate to that environment.

## Examples

Example: A database error-mapping change is checked against representative actual driver errors.

Counterexample: A successful build does not establish that an installed application opens the user's migrated files correctly.

## Adapt when assumptions change

- The change moves from pure logic to an external adapter. Add evidence at the real boundary; existing logic tests remain useful but no longer establish the full claim.
- Only a reversible text label changes. Inspect the rendered label and relevant interaction; skip unrelated system-wide checks unless required by the repository.

## Context-adapted validation probes

- The evidence directly observes the claimed outcome.
- A plausible defect at the changed boundary would fail or be visible in the selected check.

## Research update (2026-10-14)

- Code review found fewer defects than its participants expected; its main outputs were understanding and knowledge transfer. Do not count review as defect verification. — [Bacchelli & Bird, Expectations, Outcomes, and Challenges of Modern Code Review, ICSE 2013](https://www.microsoft.com/en-us/research/?p=164195)
