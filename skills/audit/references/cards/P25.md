# P25 — Explain why code exists when the reason is not obvious

Document a design's rationale when future changes depend on constraints or tradeoffs the code cannot explain, including what would invalidate the decision.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Preserve non-obvious knowledge required for future correct changes.

A nearby explanation preserves non-obvious knowledge so later changes do not erase the reason for the design.

## Context

**Source applicability:** Ordering, ownership, units, asynchronous timing, external guarantees, or historical constraints are necessary to understand a correct change.

**Avoid:** Do not restate syntax, impose a comment quota, or keep an obsolete explanation merely because it once justified the design.

**Premises:**
- The explanation adds information beyond names, types, and obvious control flow.
- It can be kept consistent with the relevant code or contract.

## Options and costs

### Explain through names and types

When: The information is simply what the implementation does.

Action: Use expressive names and types instead of comments that repeat the code.

Gain: Reduces reading clutter and explanations that become inconsistent with code.

Cost: Names cannot explain past failures, external constraints, or why alternatives were rejected.

### Explain the nearby constraint

When: A workaround, ordering rule, or safety condition would otherwise look unnecessary.

Action: Explain why the code is needed and what change would make the explanation obsolete.

Gain: Helps prevent a future cleanup from reintroducing the original defect.

Cost: The explanation must be revised when its underlying assumption changes.

### Link a decision record

When: The design depends on several alternatives, assumptions, or consequences that exceed a short local comment.

Action: Record the evidence, options, chosen tradeoff, and conditions for reconsideration, then link it from the relevant code.

Gain: Preserves the context needed to evaluate a future design change.

Cost: The record can become stale or hard to find unless its links and assumptions are maintained.

## Examples

Example: Explain why publishing must occur after a callback-sensitive initialization step.

Counterexample: An increment statement does not need a comment saying that the counter is incremented.

## Adapt when assumptions change

- A stronger type or API now expresses the previously hidden invariant. Remove redundant commentary while preserving any rationale the code still cannot express.
- The historical dependency restriction no longer holds. Reassess the implementation and update the explanation; do not retain an obsolete workaround by habit.

## Context-adapted validation probes

- A reader can explain why the unusual code exists and when it may change.
- The explanation matches the current implementation and cited dependency behavior.

## Research update (2026-10-14)

- Code and comments drift: a comment-checking tool found 60 inconsistencies (33 bugs, 27 bad comments) in Linux, Mozilla, Wine and Apache. Update or delete a comment in the same change that alters its code. — [Tan et al., /* iComment: Bugs or Bad Comments? */, SOSP 2007](https://www.cs.purdue.edu/homes/lintan/publications/icomment_sosp07.pdf)
