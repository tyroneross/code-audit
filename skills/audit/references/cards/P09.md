# P09 — Add ways to extend code only for real alternatives

Add an extension point only when real or committed variations share a stable contract and separating them is simpler to maintain than repeatedly changing the existing code.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Add real variants without repeatedly disturbing stable policy.

A stable contract localizes variation so an additional implementation can be introduced without duplicating or destabilizing common policy.

## Context

**Source applicability:** Several real variants or a committed requirement repeatedly exercise the same extension boundary.

**Avoid:** Do not create a plugin system for hypothetical variants or interpret open/closed as a ban on editing existing code.

**Premises:**
- The variation is real and its shared contract is understood.
- The extension point is simpler to maintain than repeated coordinated modification.

## Options and costs

### Implement the known cases

When: There is one case or a small set that rarely changes.

Action: Use direct code or a clear conditional for those cases.

Gain: Keeps behavior easy to read and avoids extension machinery.

Cost: Adding a new case may require editing and rechecking the existing code.

### Pass the varying operation

When: One small operation needs real alternatives while the surrounding behavior stays the same.

Action: Pass a function or simple strategy for that operation.

Gain: Supports the variation without building a general plugin system.

Cost: Callbacks and captured state can make control flow harder to follow if the boundary is poorly chosen.

### Define an extension contract

When: Several real implementations share stable behavior and need to evolve independently.

Action: Define the extension interface and verify the required behavior for each implementation.

Gain: Allows new variants without repeatedly modifying the surrounding policy.

Cost: Adds configuration, lifecycle management, and more paths to debug.

## Examples

Example: Several supported export formats share an established validation and publication contract.

Counterexample: A one-off script with one output format does not need an extensible export plugin architecture.

## Adapt when assumptions change

- Only one implementation remains and further variation is no longer expected. Consider removing unused extension machinery if doing so reduces maintenance without disrupting consumers.
- Variants no longer share the same semantics. Split the contracts or expose capabilities rather than forcing incompatible behavior into one extension point.

## Context-adapted validation probes

- A representative new variant preserves existing behavior and required guarantees.
- Adding it does not require scattered knowledge of the variant throughout the application.
