# P15 — Report failures in a form callers can handle correctly

When designing a failure contract, choose results, exceptions, or translation according to the caller's required actions and the runtime's actual propagation and cleanup guarantees.

Read [audit interpretation](../audit-interpretation.json) first. Review unsafe uses and unsupported claims even when a safe technique prerequisite is absent. Adapt validation examples to the actual contract; combine or stage options when useful.

## Purpose and mechanism

Make failures visible and usable within the actual runtime.

Idiomatic typed results, exceptions, or checked contracts make meaningful outcomes visible and composable within the actual language ecosystem.

## Context

**Source applicability:** Creating a boundary, changing how expected failures are represented, or repairing routinely missed outcomes.

**Avoid:** Do not transplant Midori's checked exceptions or abandonment model into a different runtime without its supporting assumptions.

**Premises:**
- The chosen mechanism fits the language, framework, and caller contract.
- Its propagation, cleanup, and termination semantics have been verified for the runtime in use.

## Options and costs

### Return explicit outcomes

When: Expected failures need different caller actions and the language supports a usable result type.

Action: Return success or a named failure that callers can inspect and, where supported, check exhaustively.

Gain: Makes expected failure choices visible in the function's contract.

Cost: Passing failures through many functions can add repetitive code.

### Use runtime exceptions

When: The language, framework, and callers already use exceptions with understood cleanup behavior.

Action: Use that mechanism, ensure resources are cleaned up, and catch where a useful response is possible.

Gain: Fits existing code and allows failures to propagate without a result check at every call.

Cost: Possible failure paths may be less visible; missed cleanup or overly broad catches can hide defects.

### Translate dependency errors

When: A dependency's errors do not match the decisions the application's callers need to make.

Action: Map relevant errors at the integration boundary while retaining their diagnostic causes.

Gain: Gives callers stable application outcomes instead of provider-specific details.

Cost: The mapping can lose useful distinctions or become wrong when the provider changes.

## Examples

Example: A conflict outcome carries the current version needed for a caller to choose whether to refresh or merge.

Counterexample: A goroutine must not be treated as a process-isolated failure boundary merely because a historical essay described it that way.

## Adapt when assumptions change

- A framework already defines a sound exception contract used by all callers. Use and document that contract unless a concrete problem justifies a result wrapper.
- An expected rejection is frequently missed or confused with a defect. Strengthen its representation or call-site handling and validate that callers can distinguish it.

## Context-adapted validation probes

- Callers handle representative expected failures correctly.
- Propagation does not bypass necessary state or lifetime guarantees.

## Research update (2026-10-14)

- 92% of catastrophic failures in Cassandra, HBase, HDFS, MapReduce and Redis came from incorrect handling of explicitly signalled errors; 25% simply ignored them (log-only counts as ignoring). Prefer representations callers cannot silently drop. — [Yuan et al., Simple Testing Can Prevent Most Critical Failures, OSDI 2014](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf)
- Spolsky argues exceptions are invisible in source and prefers returned error values, which sides with Chen's critique. — [Spolsky, Exceptions (2003)](https://www.joelonsoftware.com/2003/10/13/13/)
