# Tool instructions for the review workflow

`<this-skill-dir>` means the absolute directory containing the entrypoint `SKILL.md`, one level above this reference. Resolve it through symlinks before running commands.

1. **Scan.** `python3 <this-skill-dir>/scripts/scan.py <path> [<path>...]` lists signals by checklist section with `file:line`. Point it at the changed files or the operation you are working on. Run it on the code you are about to write too: the checklist applies to new code, not only old.
2. **Trace the relevant operation, then read the hits.** Follow its entry point, relevant helpers, callers and observable boundaries. Count how many times each input is fetched, parsed, queried or scanned per operation; expand the investigation when the evidence points there. Read the matching sections in the [entrypoint checklist](../SKILL.md), then the relevant code. A hit is a place to look, not a defect, and the main path still needs inspection when there are no hits.
3. **Fix the causal mechanism at the simplest adequate boundary.** Compare a symptom patch with a repair at the existing common owner when multiple supported paths are affected; use [whole-system repair](whole-system-repair.md). Remove work before adding caches, concurrency or new layers. Before any fast path ships, pass the [contract gate in entrypoint section D](../SKILL.md#d-contract-gate--must-pass-before-any-fast-path-ships).
4. **Verify with the repo's tools.** Run the original case and relevant tests; for a speed claim, time the same workload before and after on the same machine. Re-time the baseline in the same session.
5. **Log findings with an existing checklist ID:** `python3 <this-skill-dir>/scripts/outcome.py add --repo <absolute repo path> --item B7 --where src/router.ts:719 --decision <decision> [--gain "-27% p50"]`. Replace B7 with the actual matching rule. Keep foundation findings without a matching ID in the review record; do not invent an ID or force a classification. Decisions: `fixed` (changed and verified), `accepted` (real issue, not fixed yet), `kept` (real tradeoff; current code is right), `rejected` (not a real issue). `--where` is a repo-relative `file:line`. The log is written to `<repo>/.code-principles/outcomes.jsonl`; for a read-only review add `--log-file <path outside the repo>`. `outcome.py score --repo <path>` shows which checklist items find real problems.
